# DEV-083：发布后核对入口与版本说明措辞不得晚于发版

## 当前摘要（2026-11-12）

分类：**部分交付 0.23.2**（0.23.1 起记录门禁、0.23.2 起状态一致性与本地链接检查；剩余：RELEASING 永久链接规则；历史包不回改）。类型：工程/发布流程。优先级：P2。

来源：2026-11-10 下载目录 `0.19.3` 第四份报告 P2-3 与 P3-4；2026-11-12 下载目录 `0.22.0` 反馈再次指出同一问题族。映射见 [归档 MAPPING](../validation/feedback-0.19.3-2026-11-10/MAPPING.md)。

结论：0.22.0 与 0.23.0 仍在标签之后才回填 POSTCHECK/发布记录，包内留下准备态快照。0.23.1 起把回填前移为机器门禁：`tools/package.py` 在写出源码包后校验包内记录，`tools/check_release_assets.py` 在下载远端源码包后重复同一校验，`tools/check_release_records.py` 供打包前单独预检。

剩余范围：

- 报告方建议的「永久链接（按 commit SHA 固定，而非 `main`）」尚未写进 RELEASING 规则。
- 已发布的 0.22.0/0.23.0 标签与四附件保持原样，不回写、不重传；只在 `main` 的发布记录顶部加补记。

## 现象

**P2-3（当前版段晚于发版）**：v0.19.3 的 `## v0.19.3` 段在 `main` 上存在，但 tag 与 `source.zip` 内没有；时间线显示 Release 于 `12:15:07Z` 发布，回填提交 `2c78aaa` 在 `12:17:34Z` 才落地（晚 2 分 27 秒）。核对数据本身正确，问题在分发产物与项目自定的「唯一核对入口」不自洽。

**P3-4（措辞与事实不符）**：`RELEASE_NOTES_0.19.3.md` 写「源码包内的本文件保留发布前占位」「结论见本文件发布后回填段」，但文件内既无占位也无该段。

**本仓当前态（0.20.0）**：`RELEASE-POSTCHECK-2026-11-07.md` 只有到 `## v0.19.3` 为止的段，**没有 `## v0.20.0`**；`docs/validation/RELEASE-0.20.0.md` 首段仍写「源码包内的摘要表保留占位」，而该表已填真实摘要；`RELEASE_NOTES_0.20.0.md` 两处写「保留发布前摘要 / 实际摘要以 Release 与 POSTCHECK 为准」，其中 POSTCHECK 当时并无本版段。即同一问题族在 0.20.0 重现。

## 2026-11-12：0.22.0/0.23.0 复发与 0.23.1 机器门禁

0.22.0 反馈与核对结果确认：两版都是先打标签、后回填 POSTCHECK，已发布
`source.zip` 内的发布记录停留在准备态。继续靠人工顺序无法阻止复发，因此 0.23.1
按以下方式收紧：

- `src/creo_mechdog/release_integrity.py`：新增 `RECORDS_ENFORCED_FROM = (0, 23, 1)`
  与 `validate_release_records(version, source_zip=None, root=None)`。校验
  POSTCHECK 的 `## v<version>` 段、Release URL、四个附件名、种子包 SHA256、
  两份 sidecar 说明、占位词；校验 `docs/validation/RELEASE-<version>.md`；传入
  `source_zip` 时对包内同名文档重复校验，并核对包内 `version.py`、README 标题与
  两份种子清单的版本；逐 ID 核对主台账与工作卡，声明「已交付 <version>」的行
  不得在主台账仍为「开发中/未排期」。0.23.0 及更早版本跳过记录门禁，历史 tag
  仍只做四附件校验。
- `tools/package.py`：四附件门禁通过后调用同一函数；失败打印问题清单并 `return 1`，
  保留 ZIP 供排查，但必须修复记录后删除重打。
- `tools/check_release_assets.py`：下载并校验四附件后，对版本 ≥ 0.23.1 的源码包
  再跑记录门禁；失败 `return 1`。
- `tools/check_release_records.py`：本地预检入口，可在打包前单独运行。
- `tests/unit/test_release_records.py`：9 项覆盖缺段、占位词、包内过期、逐 ID
  状态不一致、缺工作卡、完整夹具、历史版本跳过与非 SemVer。
- `docs/development/RELEASING.md` 增加「0.23.1 起：回填前移」小节，明确
  「提交记录 → 构建种子 → 回填摘要 → 复建确认 → `package.py` → 标签/发布 →
  `--tag` 核对」的顺序。

包内不写 `source.zip` 自身 SHA256（ZIP 不能包含自身摘要），也不写打包时不存在
的 Release id/发布时间；这些由 sidecar 与 Release 正文承担，包内文档写明「摘要见
同名 sidecar」。0.23.1 的打包与 `--tag` 核对结果见
[RELEASE-0.23.1](../validation/RELEASE-0.23.1.md) 与统一 POSTCHECK。

## 2026-11-13：0.23.2 状态一致性与链接门禁

0.23.0 目录反馈确认：0.23.1 的逐 ID 子检查只在主台账状态恰为「开发中/未排期」
时生效，FEAT-066 的表卡矛盾连续两版；版本说明相对链接第三次断链。0.23.2 收紧：

- 状态归一化为 `delivered / partial / developing / unplanned / other`，工作卡只读
  `分类：` 行的粗体状态，避免长摘要里的「已交付」把「待复现」误判为已交付。
- 逐 ID 表检查「技术状态」「卡首页」「主台账」与工作卡状态；「主台账」列必须与
  真实台账状态逐字一致；允许用「差异说明」列显式记录保守措辞差异。
- 扫描主台账所有 `work-items/` 活动行中状态类为 `partial`/`delivered` 的 ID，
  不只检查发布记录表；归档行跳过。
- `_link_problems()` 检查发布说明、发布记录与 POSTCHECK 的本地相对链接；根模式
  与源码 ZIP 模式都检查，外部链接与纯锚点跳过，逃出包根的链接直接拒绝。
- `tests/unit/test_release_records.py` 扩到 15 项，覆盖部分交付+已交付卡、差异说明
  放行、主台账列不一致、发布表外全表扫描、断链与 ZIP 内断链。
- `docs/RELEASE_NOTES_0.23.0.md`、`docs/RELEASE_NOTES_0.23.1.md` 与
  `docs/validation/RELEASE-0.23.1.md` 修正断链；历史标签与附件不重传。

仍开放：RELEASING 中按 commit SHA 固定永久链接的规则。0.23.2 的打包与 `--tag`
核对结果见 [RELEASE-0.23.2](../validation/RELEASE-0.23.2.md) 与统一 POSTCHECK。
