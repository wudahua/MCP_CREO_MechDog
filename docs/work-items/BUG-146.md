# BUG-146 恢复作业停在 intent_persisted 且旧所有者不可确认

分类：**已有修复但待验收**（0.35.6 交付；原：待复现/待核实）

类型：缺陷。优先级：P1。目标版本：未排期。

0.34.0 的挂死后恢复进入 queued，报告的 owner PID 已消失。关联 BUG-074、BUG-131；旧会话消失不能单独证明本机写入进程已停止。Windows 离线模拟意图落盘、退出和 PID 复用，确认作业可诊断、可安全判终态，且旧进程存活、身份不明、revision 或证据失配继续受保护。重启后的健康磁盘基线恢复另做实机。

来源：[本批反馈计划](../archive/development/0.35.0-FEEDBACK-PLAN-2026-11-21.md)。

本轮全量测试另复现恢复证据无法落盘：工作树目录较深时，`evidence-<ID>.json` 本身可创建，原子写入临时名再附加 UUID 后超过 Windows 路径限制，恢复检查返回 `FileNotFoundError`。使用同目录短临时名，保留排他创建、原子替换与异常清理；用长路径和 DEV-040 stdio 夹具验收。

离线验证：真实文件锁对照通过，已经接受的 runner 等提交锁释放后继续执行。超时仍保留待恢复状态，既有证据与 revision 保护通过回归。短临时名及 DEV-040 stdio 长路径用例均通过。原报告中未成功启动的旧恢复作业、Creo 会话重启后恢复和实际文件均待实机重现。

## 本轮修复（开发分支 `codex/bug-144-release-evidence-plan`，基线 `98c598f`）

死局根因：恢复作业的 runner 在拿到通道前把 `runner_identity` 作为第一条持久记录写入；如果服务在“意图已落盘”和 runner 首次写入之间退出，作业会永久停留在 `queued`/`intent_persisted`。`native_owner.json`、`worker_started` 都不存在时，所有权既不能证明“在跑”，也不能证明“已停”，于是 `stopped=false` 锁死全部动作——包括唯一能修复磁盘基线的 `restore_baseline`。

- 记录启动者：恢复作业在 `Popen` 之前把 `launched_by`（pid + 创建时间）写进 `job.json`，成为“谁写下这个意图”的独立证据。
- 可判定：新增 `_stalled_intent()`。只有同时满足 `kind=reconciliation`、`stage=intent_persisted`、`status` 为 `queued`/`waiting_for_channel`、`worker_started=false`、无 `runner_identity`、无任何 native 文件、启动者按 PID+创建时间可证明已退出（进程不存在，或同 PID 但创建时间不同＝PID 复用）、意图已存在超过 120 s 时，才判定“从未启动”，并把 runner/worker 记为已停止。
- 仍受保护：启动者存活、身份不可读（`alive=None`）、缺 `launched_by`（0.35.5 之前的旧作业）、`worker_started=true`、存在 `native_owner/checkpoint/result` 任一文件时，全部维持原判定，`stopped=false`。
- 诊断：`creo_reconcile_model` 的 inspect 新增 `stalled_recovery`（proven/basis/launcher/observed/age/grace/limits）与 `recovery_wait`（state/reason/detail/next_step），直接回答“为什么一直 queued”。
- 终态出口：新动作 `abandon_stalled_recovery`（需 `confirm_stalled_recovery=true`）。metadata only：不取 Toolkit、不启 worker、不写模型文件，把该意图记为 `failed`/`intent_abandoned`、`reason=recovery_intent_never_started`，只释放 `recovery_pending`。`pending_job`、`revision`、`part_file`、模型状态与会话保护都不变，随后仍需模型自己的 reconcile 动作。幂等键沿用既有 `intent-<digest>.json` 日志，重放返回同一结果。
- 顺序：先释放 `recovery_pending` 再写终态作业记录，中断只会留下孤儿作业记录，不会留下“指向终态作业的保留”，避免再次被判成不可证明。
- 证据绑定：`stalled_recovery` 不进入 `_binding()`，否则每次读取变化的 `age_seconds` 会让刚发出的 `evidence_token` 立即过期。

## 实机（2026-11-21，Creo 10.0.0.0，由 BUG-143 固体镜像挂死现场自然产生）

- 现场：模型 `40b6881df15041898ff253fa41c3a900` 的实体块体积 1999.9999999999998 mm³，`saved_reloaded` 校验通过；随后的固体镜像作业 `7b7be35e13fd42b5bfca92f4d36250ae` 卡死（见 [BUG-143](BUG-143.md)），会话随后 `toolkit_code=-38`。
- 重启 Creo 后 `creo_reconcile_model(inspect)`：`baseline.verified=true`（sha256 `e8c045431ffa75cb395bf723fd8c5a8a506260fa7cf9c7d6d8bf3e47595c966b`、100,850 字节）、`candidate` 指向同一文件、`pending_job=7b7be35e…`、`restore_baseline.available=true`；三个 owner 的 runner/worker 均 `stopped=true`（`windows_error=87`，即 PID 已不存在）。
- 首次 `restore_baseline` 随客户端退出中止：作业 `f0f37ef57d8f40d0908146d6d8beecdd` 停在 `queued`/`waiting_for_channel`、`worker_started=false`、`launched_by` 的 pid 15088 已消失。这正是 0.34.0 反馈的形态，但 stage 已推进到 `waiting_for_channel` 且留有 runner 记录（pid 20216，已退出）。旧规则只认 `intent_persisted` 且无 runner 记录，于是 `stalled_recovery.reason=stage_advanced`、`abandon_stalled_recovery` 不可用——真实残留暴露出判定边界过窄。
- 规则扩展（本轮代码，`src/creo_mechdog/reconciliation.py`）：pre-worker 的两个阶段（`intent_persisted`、`waiting_for_channel`）都纳入判定；记录的 runner 不再一律拒绝，而是必须可证明已退出（进程不存在，或同 PID 不同创建时间），存活或不可读仍保护。`recovery_wait` 的 `next_step` 按原因分支（`stage_advanced`、`runner_still_alive`、`launcher_still_alive`、`within_startup_window`）。新增 4 项单测，`test_bug146_stalled_intent` 15 项通过。
- 扩展后同一现场：`stalled_recovery` → `proven=true`、`basis=runner_exited`、`stage=waiting_for_channel`、`age=153.15 s`（> 120 s 宽限）；`recovery_wait.state=stalled_intent_proven`，reason 为“runner 在 native worker 启动前退出”。
- `abandon_stalled_recovery`（`confirm_stalled_recovery=true`）把 `f0f37ef5…` 记为 `failed`/`intent_abandoned`，`revision` 仍为 1，`pending_job`、`part_file`、会话保护未变。
- 随后 `restore_baseline` 首次返回 `unknown_outcome`：`stage=reconciliation_unconfirmed`、`worker_started=true`，消息为 “Recovery refused: Creo session changed since recorded evidence; native worker dispatch began and may have started”。即用重启前会话的证据派发被拒，保护保留，`recovery_pending` 指向该作业。
- 重新 inspect 取当前会话证据后再次 `restore_baseline`：作业 `209184e0154b442890f13e4549045880` `succeeded`、`stage=reconciliation_committed`；模型 `pending_job=null`、`recovery_pending=null`、`status=ready`、`revision=1`，`resolution.source_identity.sha256=e8c04543…`，几何 1999.9999999999998 mm³、`inspection_source=reconciliation_verified`、`healthy=true`。

观察（未单独立项）：会话变更后的第一次 restore 仍会先派发 worker 才拒绝，留下 `unknown_outcome` 和一次 `recovery_pending`，必须重新 inspect 才能继续。可考虑在派发前先比对会话指纹，省掉这次无效派发。
