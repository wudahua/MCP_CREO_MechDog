# BUG-149 客户端退出后只读作业永久占用模型

分类：**已有修复但待验收**（0.35.7 交付修复；Creo 10 实机用真实残留闭环）

类型：缺陷。优先级：P1。目标版本：0.35.7（修复已交付）；真实退出时序与 Creo 9/12 未排期。

0.35.6 的 T10 补验两次撞到同一死局：客户端在只读质量查询结束前退出，作业留在 `unknown_outcome`（`termination.attempted=false`、`reason=no_runner_pid`），模型继续以该作业为 `pending_job`。此后任何请求都被 `toolkit_busy`「Model has a pending job」拒绝，`creo_cancel_job` 因作业已终态只回「nothing was cancelled」，而现有恢复动作没有一个接受这种占用。

来源：[本批反馈计划](../archive/development/0.35.0-FEEDBACK-PLAN-2026-11-21.md)、[FEAT-073](FEAT-073.md) 的 T10 补验记录。

## 根因

只读计划在准入上被限制为 `INSPECTION_ONLY_OPERATIONS`（`dump_tree`/`export`/`udf_inspect`/`mass_properties`/`surface_group_measure`/`surface_curvature`），因此它不可能改变几何、`revision` 或已保存文件。但三处代码把只读作业当成了可写作业：

1. `run_generic_job` 在超时、看门狗停滞、`native_result.json` 缺失、交付未确认等分支里把模型置为 `unknown_outcome`，并在收尾处无条件 `model["pending_job"] = job_id if manifest["status"] == "unknown_outcome"`，未判断 `readonly`。
2. `cancel_job` 把 `unknown_outcome` 当作不可再动的终态直接返回；同时 `_terminate_process_tree(None)` 只会记 `no_runner_pid`，却在 `runner_pid is None` 时仍把作业判为已终止，并按可写作业写 `geometry_may_have_changed=true`、保留模型占用。
3. 恢复侧没有出口：`ack_no_mutation` 要求 `status=failed` 且有校验过的检查点，`ack_failure`/`abandon_stalled_recovery` 要求模型不持有 pending/recovery 作业，`restore_baseline`/`accept_saved`/`accept_live` 要求候选或实时证据。只读作业没有任何一条满足。

## 修复

- `run_generic_job`：进入时取一次 `readonly` 与 `admitted_status`（准入已证明 `ready`）。所有不确定分支对只读作业保留 `admitted_status`、收尾不写 `pending_job`，消息明确“作业结果未知、模型未变、可重新查询”。`ToolkitBusy` 分支对只读作业释放自己从未派发的占用（占用者是别的模型作业，不会互相覆盖）。
- `cancel_job`：新增 `_job_readonly`（以 `job.json` 的入参标志为准，旧作业回落到 `request.json`；读不到即按可写处理）。只读作业 `geometry_may_have_changed=false`，并走新增的 `_release_readonly_reservation`——只改模型记录（清 `pending_job`；仅当状态是本类作业自己写下的 `unknown_outcome` 时恢复 `ready`），前提是模型仍持有该作业且该作业记录的 runner/worker 均不再存活（`taskkill` 成功即以其为停止证据，无需再探活）；对已经终态的历史占用同样生效，回执带 `readonly_release`。
- `creo_reconcile_model` 的 inspect 增加 `readonly_pending` 块：直接指出这是一次只读占用、其唯一出口是带该 `job_id` 调 `creo_cancel_job`，不占用任何 native 工作。
- 新增 `tests/unit/test_bug149_readonly_release.py` 13 项：交付缺失/交付未确认/超时都不锁模型，同条件下可写作业仍锁（回归保护）、`ToolkitBusy` 只释放只读占用、终态只读占用释放、存活 owner 拒绝释放、可写终态作业行为不变、第二次取消不重复声明释放、inspect 诊断。

## 实机（2026-11-22，本机 Creo 10.0.0.0）

现场就是 0.35.6 补验留下的真实残留：模型 `0ce7c04e57bb4dc08b149a1fe64542d2`（`t10a_13_111744`，`revision=1`，`part_file` 存在）与只读作业 `07e6f30d8c1c4bc6989ae2e9b5466f96`（`readonly=true`、`worker_started=true`、`runner_pid=null`、`cancellation.termination={attempted:false, reason:no_runner_pid}`）。

| 步骤 | 结果 |
| --- | --- |
| 释放前提交只读 `mass_properties` | 拒绝：`toolkit_busy`「Model has a pending job」，`blocking_job_id=07e6f30d…`、`blocking_operation=pending_job` |
| `creo_cancel_job("07e6f30d…")` | `cancelled=false`、`status=unknown_outcome`；`readonly_release.released=true`、`previous_model_status=unknown_outcome` → `ready`、`revision=1` 未变；`next_steps` 指向重新查询 |
| 释放后模型记录 | `status=ready`、`pending_job=null` |
| 释放后同一模型再提交只读查询 | 受理，作业 `881b44fcb84a44e5884b2085be95bf83` `succeeded`、`stage=verified`、`readonly=true`、体积 `1150.0 mm³`、`revision` 仍为 1 |
| 只读作业在编译预检失败（`fed46374…`，`worker_started` 未起） | 模型保持 `ready`、`pending_job=null`，即新不变量在真机生效 |

证据：`build/bug149/live_20261122T161657.json`（释放前后完整记录与两次提交回执）、`build/bug149/requery_20261122T161806.json`（重查作业）。驱动脚本 `build/live_bug149_release.py`、`build/live_bug149_requery.py` 属构建目录，不入发布件。编译预检所需的 `vcvars64_env` 为当次临时配置，用后已还原为 `null`。

## 未验

- 真实“客户端中途退出”本身：复现的是它留在磁盘上的等价状态（终态只读作业 + 模型占用 + 无 runner pid），退出时序未在协议层抓取。
- Creo 9/12、外部反馈环境与 WorkBuddy 黑盒。
- 只读作业与并发的其它模型作业同时占用通道时的释放时序（单通道串行下未构造并发）。
