# BUG-122：已知内核拒绝元素树仍建空壳，surface_loft 应在提交前拒绝

## 当前摘要（2026-11-13）

分类：**部分交付，剩余待验收**。类型：缺陷/兼容性。优先级：P1。目标版本：0.24.0（子项）；剩余未排期。

来源：`C:\Users\Administrator\Downloads\反馈包-球鼻艏-20261112` 主报告第 12.1 节：`kernel_completion="unsupported"` 只披露，`surface_loft` 仍会提交、在模型里留下 `PRO_FEAT_ACTIVE` 的不完整特征，再靠整作业回滚清掉。

结论：0.23.2 的观测记录（`build/toolkit_health.json` 的 `surface_loft_runtime`，按 worker SHA 键控）已足以在提交前判定，但当时声明为"仅披露"。本轮把**同一 executor 上实测到的内核签名**接进准入：`kernel_completion=unsupported` + `create_code=0` + `extract_code=-18` 才拒绝；缺观测、跨 worker、或失败的 create 一律不拒绝，避免一次回滚锁死会话。

## 现象与证据

- 反馈 E9：`create_code=0`、`extract_code=-18`、`feature_incomplete=true`、`release_numeric=42`，A/B 诊断字段到位后现象不变。
- 反馈 12.1 明确要求"`kernel_completion=="unsupported"` 且 `release_numeric` 未变时直接拒绝，不建特征"。

## 本次改动

- `src/creo_mechdog/capabilities.py`：新增 `require_kernel_completion(operations, identity)`；只在条件操作（`WORKER_CONDITIONAL_OPERATIONS`）上生效，且要求 `_verified_worker_feature` 已验证、观测为 `unsupported`、`kernel_evidence.create_code == 0` 且 `extract_code == -18`。拒绝文本给出证据、worker SHA、`job_id` 与三条出路，并声明"按 worker SHA 键控，新构建即清除"。
- `generic_bridge.py`：`submit` 在 `require_worker_availability` 之后、取得通道之前调用同一身份对象；拒绝时不建 job、不留 pending。
- `capabilities.project_worker_availability`：编译可用性（`available`/`enabled`）不变，但签名匹配时新增 `runtime_admission={status:"refused_before_job", ...}`，避免能力表读成"可直接调用"。
- `bridge.record_surface_loft_runtime` 文档更正：不再是"仅披露"，但准入只读同一 worker 的实测签名。
