## 1. ❌ P1（核心问题）：草图弧无 dir 参数且恒 CCW —— 仍未修，且新诊断层同源失效

### 1.1 静态证据（0.7.0 源码）

**(a) Schema 无 `dir` 字段。** `src/creo_mechdog/schema.py:139-148`：

```python
class Arc(Circle):
    type: Literal["arc"]
    start_angle: float
    end_angle: float
    # validator 仅拒绝整圆（|end-start|%360 < 1e-10），无方向字段
```

**(b) 原生侧恒强制 CCW，两处同源代码均未改。** `native/generic.cpp:1362` 与 `:2164`：

```cpp
if (a.end_angle <= a.start_angle)
    a.end_angle += turn;   // 恒把 end 抬到 start 之后 → 恒 CCW，无 >180° 告警
```

### 1.2 实机对照实验（同图元，仅角度书写顺序不同）

草图：圆心 (0,0) R10 弧 + 弦 (10,0)→(0,10)，extrude depth 5。

| 模型 | 弧书写 | 体积 (mm³) | `profile.material_area_mm2` | status | 告警 |
| --- | --- | --- | --- | --- | --- |
| `rt07_arc_ccw`（`f2ad12ec…`，job `c2d6b385…`） | `start=0°, end=90°` | **142.69908169840258** | 28.53981633974483（劣弓形 ✓） | succeeded | 无 |
| `rt07_arc_cw`（`d3bdd069…`，job `c2b491f1…`） | `start=90°, end=0°` | **1428.0972451017306** | **285.6194490192345**（优弓形） | succeeded | 无 |

- 体积与 0.3.3 / 0.3.5 两轮实测值**逐位一致**（142.699081698… / 1428.097245101…），确认行为自 0.3.0 报告以来**从未变化**。
- 理论值：劣弓形 ×5 = 142.6990816987 ✓；优弓形 ×5 = 1428.097245102 ✓。体积差 **10.007 倍**，两次均 `success:true`、零 warning、零 error。

### 1.3 ⚠️ 新发现：T06 诊断层与缺陷同源，参考面积跟着错

这是本轮最重要的新观察。T06 的 `profile` 诊断（Python 侧 `profile_diagnostics.py`）按输入图元计算 `material_area_mm2` 作为参考面积：

- CCW 书写（正确意图）→ 报 **28.54 mm²**（与实体一致）；
- CW 书写（同一几何意图）→ 报 **285.62 mm²**（与实体一致，但与用户意图相反）。

也就是说：**分析器与原生建图元共用同一条"恒 CCW"归一化规则**。这带来两个后果：

1. **诊断层永远无法发现方向歧义**——无论用户怎么写角度，`profile` 面积总是与最终实体精确吻合，所有校验闭环自洽，缺陷彻底隐形；
2. **错误几何现在多了一层"已通过 T06 校验"的背书**——`profile.categories` 全 0、`analysis: complete`、面积与体积互证一致，调用方更难怀疑。

对逆向重建类任务（逐特征体积/面积/惯性比对验收），这仍是唯一能穿透全部数值验收的静默错误几何路径。

### 1.4 建议（第三次提出）

1. **`Arc` 增加 `dir` 字段**（`+1`=CCW / `-1`=CW，默认 `+1` 保持兼容），原生与分析器同规则消费；
2. **至少加告警**：当分析器算出的扫过角 `> 180°` 时，在 `profile` 里加 `sweep_warnings`（例如 `"arc 'a1' sweeps 270°; verify start/end order"`）——成本最低，且能同时暴露"分析器面积跟着走"这一点；
3. 若维持"合法大弧不在支持范围"的边界决定，请把它作为**显式待办条目**登记，而不是留在 `success:true` 里。

## 2. ✅ P3 → T06：自交轮廓诊断已修，实机验证通过

蝴蝶结 polyline `(0,0)→(20,0)→(0,20)→(20,20)` 在 0.7.0 的实测表现（与 0.3.3/0.3.5 对比）：

| 项 | 0.3.5 | 0.7.0 |
| --- | --- | --- |
| 结果 | Toolkit 阶段失败 | **MCP 准入阶段直接拒绝**（`Error executing tool`） |
| 错误内容 | `ProFeatureWithoptionsCreate failed with code -1` | `"operations[1]: Solid extrude profile rejected: detected 1 closed contour(s), 0 open contour(s) and 4 curve entities; [self_intersecting] a self-intersecting contour (bow_1/bow_3) near (10, 10) mm; [zero_area] a zero-area contour (bow_0/bow_1/bow_2/bow_3). Supply disjoint or nested closed loops; …"` |
| 结构化分类 | 无 | `[self_intersecting]` + `[zero_area]` + 实体名 + 交点坐标 |
| Toolkit 通道 | 占用一次并失败 | **未占用**（准入拦截，未建模型登记、未留垃圾） |

这正是 0.3.3 反馈中"提交前做自交预检并返回结构化 errors"的建议原样落地，且实现质量好：分类文本可操作（指明 `bow_1/bow_3` 相交于 (10,10)），`fatal` 分类集合（open/branched/self_intersecting/intersecting/tangent/zero_area）覆盖合理，unsupported 实体（ellipse/spline）明确跳过判定留给原生 solver。

**一个建议**：准入拒绝发生在 `creo_execute_plan` 工具调用内（以 isError 形式返回），目前没有独立于"建模失败"的通道级错误码。如果未来要自动化区分"输入被拒"与"建模失败"，可考虑在错误消息前缀或结构化字段上区分（如 `rejection_stage: "admission"`）。现状对人工使用者已完全够用。

## 3. ✅ P5 → 装配位姿矩阵输入已修，实机验证通过（本机最重要的验证）

`native/assembly_pose.h` 新增 `rotation_matrix` 输入路径：3×3 嵌套数组，正交性 1e-6 + det=+1 校验，与 `rotation` 互斥（Python `AssemblyPose` 与原生双重检查）。行向量约定与平移在最后一行保持不变，头注释明确声明 "Never repair input poses"。

**实机验证**：取 pump_asm 中万向锁实例 I004（P07 齿轮 A，`|ry|=90°`）的实测 4×4 transform 的旋转部分，直接作为 `rotation_matrix` 提交新建装配：

| 项 | 结果 |
| --- | --- |
| job | `9f377d986fc84f6281a174cc49168150`，模型 `rt07_asm_matrix`（`ef36ab90…`） |
| status | succeeded，rev 1，`saved_file_reloaded_and_verified=true` |
| 实际存入 transform vs pump_asm 参考实例 | **旋转 16 元素逐元素差 0.000e+00；平移逐元素差 0.000e+00** |
| 体积 | 14214.879368534603 mm³（与 P07 零件 rev 2 完全一致） |
| 对比欧拉角路径 | 0.3.3 轮同实例欧拉角（锁点 rz=0 + 9 位小数）残差为 4.882e-08 |

**结论**：矩阵直填彻底消除了万向锁量化残差和 `rotation=[0,90,0]` → Ry(−90°) 的符号陷阱——调用方不再需要理解欧拉角约定，直接从规格矩阵喂入即可。这是对我逆向重建工作流价值最大的一项修复。`component_changes`（status/changes/label/feature_id/source_model_id/source_revision）也在同一 job 中得到验证。

## 4. ❌ P4：组件 model_name 仍是 job-id 派生名（缓解已有，未根治）

`native/advanced.cpp:537-542` 与旧版逐字同源：

```cpp
swprintf_s(copy_name, L"c_%s_%u", token.substr(0,16).c_str(), …);
ProMdlnameCopy(child, copy_name, &copy);
```

0.7.0 实读（`rt07_asm_matrix` 的 components 分节）：`model_name = "C_9F377D986FC84F62_0"`，组件记录无 `label` 字段。

**缓解已存在**：同 job 结果新增 `component_changes`（`{"op":"added","label":"gear_ref","feature_id":40,"source_model_id":"…","source_revision":2}`），`creo_list_components` 的 aliases 也可恢复 label→feature_id 映射。但 `inspect_model(section=components)` 的每条记录里 `model_name` 与用户 label 仍是两套命名，跨 job 汇总时仍需 join。

建议：组件副本名直接用 label（或 `label_<n>`），或 components 记录里加 `label` 字段——一行序列化的成本。

## 6. ⚠️ P7：revolve 轴 —— 部分改善，结果回显仍缺

**改善的部分**（实测确认）：
- `datum_axis` 操作结果新增 `origin/direction/geometry_known` + 5 项查询码（T05）；
- 无效 `axis` 引用有可操作的报错（`validate_revolve_axis` 列出三种合法写法）；
- 新示例 `examples/revolve_external_axis.json` 提供标准用法，实测（job `035e01ca…`，Ø10×10 环，体积 3141.592653589793 与解析值逐位一致）外置轴回转完全正确。

**仍缺的部分**：
- `revolve` 操作结果仍只含 `material_removed_mm3`（cut 时）与 `length_unit`——**不回显实际解析使用的轴**（id/label/origin/direction）。含多根 centerline 或多 datum axis 的草图上，"静默选了一根"仍无法从结果侧发现；
- 省略 `axis` 时 `validate_revolve_axis` 直接 return（`native/generic.cpp:1562`），内部中心线回退依旧静默。

建议：revolve 结果加 `resolved_axis: {"kind": …, "id": N, "origin": […], "direction": […]}`，或在省略 axis 时报一行 `axis_source: "sketch_centerline"`。
