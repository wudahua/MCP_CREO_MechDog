> 反馈对象：MCP_CREO_MechDog 作者
> 实测环境：Creo Parametric **10.0.0.0**（`release_numeric=42`）/ MCP_CREO_MechDog **0.23.0**
> worker `sha256=fe166f16de74bb5d0e2e46db7c72eb32308755aaf2c24e67173add1b2dee08cc` /
> `source_digest=549200ae53d2dc19565e91be6cbb8040da795307407f50c2435f50be7fac3477`
> 任务约束：用户要求「球鼻艏按 MCP 曲面能力继续推进，**不要近似方法**；发现问题写清楚」
> 关联：`2026-11-12+CREO+0.22.0+边界混合在Creo10不可提取元素树与has_solid全局误判.md`（0.22.0，部分结论已被本文更新）

## 一、结论先行

**先说三件好事，都是本版真机实测。**

1. **DEV-082 门禁修复有效**。0.23.0 在 Creo 10 上 `surface_loft` 首次变为
   `available=true / state="compiled"`，`missing_sdk_requirements=[]`，
   提交**不再被前置拒绝**，真正跑进了原生作业。
2. **Creo 10 内核接受这个边界混合元素树**。作业回执里
   `create_code = 0`、`create_element_errors.total = 0` ——
   `ProFeatureWithoptionsCreate` 在 Creo 10 上**成功建出了边界混合特征**。
   这推翻了我上一份反馈里的推断「补头文件也没用，内核不会认」，**我收回那句话**。
3. **FEAT-066 `b_spline` 在 Creo 10 上完全可用**，形状保真到 `2.33e-13 mm`（§5）。

**但球鼻艏仍然没做成**，卡点已经从「门禁」downstream 移到「补全」：

> 实现路线是「先建**不完整**特征 → **回读**元素树拿到内核默认值 → 用补全后的树 `redefine` 触发再生」。
> Creo 10 能走第一步（`create_code=0`），但**不能回读**（`extract_code=-18`），
> 于是整单回滚，`rollback_succeeded=true`，模型干净、无残留。

也就是说：**这不是"Creo 10 做不到边界混合"，而是"这条实现策略需要的能力 Creo 10 没有"。**

## 三、源码定位：卡点在「补全」，不在「创建」

`native/surface_loft.cpp`：

```cpp
// 文件头 7–11 行
// …its element ids live in ProElemId.h (Probbl.h only documents them
// and defines PRO_E_DTM_SRF_TYPE_BND_BLEND). … so this implementation
// builds the bare skeleton first and completes it from the extracted tree
// instead of guessing element values.

// 27–31 行：作者已给出兜底值（真值 = 11）
// Probbl.h defines this one macro and nothing else; keep its documented value
// when the documentation header is absent.
#ifndef PRO_E_DTM_SRF_TYPE_BND_BLEND
#define PRO_E_DTM_SRF_TYPE_BND_BLEND 11
#endif

// 957 行：建“不完整”特征
ProError created = ProFeatureWithoptionsCreate(solid_selection, root, options,
                                               PRO_REGEN_NO_FLAGS, &feature, &element_errors);
//    options[0] = PRO_FEAT_CR_INCOMPLETE_FEAT;   (954 行)

// 987–994 行：回读元素树（Creo 10 在这里 -18）
ProError extract_code =
    ProFeatureElemtreeExtract(&feature, nullptr, PRO_FEAT_EXTRACT_NO_OPTS, &extracted);
if (extract_code || !extracted) { … throw "… cannot extract the created feature tree" … }

// 1018–1022 行：回读的必要性 —— 这就是“补全”
// The extracted tree is completed by the kernel's own defaults; redefining
// with it is the regeneration the incomplete create skipped.
redefine(&feature, extracted);
```

链条是闭合的：

1. 用 `PRO_FEAT_CR_INCOMPLETE_FEAT` 建特征 → **成功**（Creo 10 上 `create_code=0`）；
2. **回读**这棵树，拿到内核自动填好的默认值 → **Creo 10 拒绝（-18）**；
3. 用补全后的树 `redefine()` 触发再生 → 走不到。

所以 §1 的定性成立：**能力缺口从 `Probbl.h` 移到了 `ProFeatureElemtreeExtract`，
但后者在 Creo 10 上是 SDK 级硬限制（官方文档明示），不是装配问题。**

## 四、给作者的核心建议：用几何校验替代元素树回读

`extract` 在这条链路里承担两件事：**拿内核默认值补全** + **作为成功凭据**。
第二件事 MCP 已有完整的替代品，第一件事需要换一种触发再生的方式。

### 4.1 建议 A（最小改动）：`extract` 失败不再整单回滚

现在 `extract_code=-18` 会 `throw` → 整单回滚，于是连「建成了什么」都看不到。
建议改成：`extract` 失败时**保留特征**，改用现成的几何度量判定，并把
`extract_code` 作为警告字段返回：

```json
{ "route": "probbl_boundary_blend", "create_code": 0, "extract_code": -18,
  "extract_unsupported": true,
  "verification": "geometry_only",
  "quilt_count": 1, "quilt_id": 57, "surface_area_mm2": 12345.6,
  "quilt_closed_native": "open", "surface_group": { … } }
```

这些字段的实现全部已经存在（`ProFeatureGeomitemVisit(PRO_QUILT)`、`ProQuiltInit`、
`quilt_area_native`、`quilt_closed_native`、`surface_group_receipt`），
**不需要任何 Creo 12 独有符号**，在本机 Creo 10 上都能跑。

### 4.2 建议 B（真正的修复）：不加 `INCOMPLETE` 标志，或事后强制再生

`PRO_FEAT_CR_INCOMPLETE_FEAT` 的作用是「先别再生」。如果创建树本身已经足够完整，
可以直接不带该标志，让内核一次再生；或者创建后显式调用 `ProSolidRegenerate`
/ `ProFeatureRegenerate`，再用 §4.1 的几何度量验收。

文件头注释提到 2026-11-01 探针「把完整树一次写进去 → 特征停在 `PRO_FEAT_UNREGENERATED`」，
但那次把 `PRO_E_EXT_SURF_CUT_SOLID_TYPE` 和 `PRO_E_BNBLN_TAN_COND*` 也塞进了创建树
（§2.1 明确禁止）。**「完整的、合规的树 + 不带 INCOMPLETE 标志」这个组合似乎还没试过**，
在 Creo 10 上尤其值得一试——因为本机已证明 Creo 10 接受这棵树。

### 4.3 建议 C：把 `create_code` / `extract_code` 的语义写进文档

现在 `failed_toolkit_call` 是 `null`、`toolkit_code=-1`，只有 `message` 里带 `-18`，
读者很难判断是「创建失败」还是「校验失败」。回执里既然已有 `create_code=0`，
建议在 `message` 里直接区分：
`"surface_loft created the feature (create_code=0) but this Creo release cannot extract
its element tree (extract_code=-18); verification fell back to geometry"`。

## 五、FEAT-066 `b_spline`：本版最有价值的进展，Creo 10 实测通过

用 TXT 附录 A20（`side_guide`，1 m→100 mm 换算后）的三次 NURBS 原样写入 Creo 10：

| 输入 | 值 |
|---|---|
| `degree` | 3 |
| `control_points` | (6409.4736,180) (6509.4736,180) (7006.7197,204.7741) (7809.4736,33.3333) (7809.4736,0) |
| `knots` | `[0,0,0,0,0.595088181,1,1,1,1]`（5+3+1=9 ✓，clamped ✓，非降 ✓） |
| `weights` | `[1,1,1,1,1]` |

job `9fd5ad9b81614e93a7c334a08fee4d3d`，rev4，`succeeded`，单条 `b_spline` 实体：

| 指标 | 实测 |
|---|---|
| **形状偏差** | **`2.3302533660563e-13 mm`** |
| 总偏差 | `0.0036178999980620574 mm` |
| 偏差性质 | `rigid=true`，`translation_mm = {u:-1.53e-13, v:-0.0036179}` |
| 求解器 | `used="autodim"`，`selection_reason="unsupported_coordinate_entity"` |

**解读**：曲线形状被精确复现（`1e-13 mm` 量级），唯一的 3.6 µm 是 `autodim`
自动标注引入的**刚体平移**，与曲线形状无关，可通过后续尺寸约束或整体补偿消除。
这解决了前几轮的核心痛点：以前只能用 200 点折线近似 NURBS，
现在 TXT 的「degree + 控制点 + knots + 权重」可以 1:1 进入 Creo。

**小建议**：`b_spline` 目前只能走 `autodim`，而 `autodim` 会带来刚体平移。
如果能在 `dimensioning="coordinates"` 模式支持 `b_spline`（至少对控制点做坐标标注），
这类「形状精确但位置漂移 3.6 µm」的问题就能从根上消掉。

## 六、仍未修：`has_solid` 全局误判（P2，0.22.0 已报）

0.23.0 release notes 原文：「0.22.0 已披露的限制不变：… 已有实体模型中的 `surface_loft`」。
源码 `native/surface_loft.cpp:1083` 仍是：

```cpp
details["has_solid"] = inspection(false)["has_solid"];   // 整个模型的全局状态
```

只要模型原本有实体（例如护卫舰船体主模型 `frigate_txt_rebuild`，`has_solid=true`），
无论放样是否只生成开放 quilt，都会判为「创建了实体」并回滚。
本轮试验刻意用了无实体新零件，就是为了把这条干扰隔离掉——
**这也意味着 §2.3 的失败与 `has_solid` 无关，纯粹是 extract 造成的。**
修法同 0.22.0 反馈：改为操作前后增量。
