## 5. 本轮问题

### P2-1 逐 ID 状态仍未统一，且 DEV-083 门禁的逐 ID 子检查覆盖面不足

`RELEASING.md:39` 第 8 步要求逐 ID 核对状态、实际交付版本、开放范围与五处链接。0.23.1 虽然新建了「逐 ID 状态核对」表，但同文档内部及与主台账之间仍有措辞冲突：

| ID | `docs/BACKLOG.md` 状态 / 目标版本 | 工作卡首行 | `RELEASE-0.23.1.md` 逐 ID 表 |
| --- | --- | --- | --- |
| BUG-119 | `已有修复但待验收` / `0.23.1（已交付子项）` | `已交付 0.23.1（Creo 12.4.0.0 实机验收…）` | 技术状态 `已实现并实机验收`、卡首页 `已交付 0.23.1`、主台账列 `已有修复但待验收` |
| DEV-083 | `部分交付，剩余待验收` / `0.23.1（已交付子项）` | `已交付 0.23.1，历史包不回改` | 技术状态 `门禁已实现并接入打包/核对`、主台账列 `部分交付，剩余待验收` |
| FEAT-066 | `部分交付，剩余待规划` / `0.23.0（已交付子项）` | `已交付 0.23.0（剩余范围未排期）` | 不在本版逐 ID 表内 |

FEAT-066 的表行「部分交付，剩余待规划」与工作卡「已交付 0.23.0」自 0.23.0 起**连续两版未统一**。可以理解作者的意图是「整体工作卡还有 `closed`、`dimensioning="coordinates"` 等未排期范围，故主台账保守写部分交付」，但两种措辞并存会让逐 ID 核对失去唯一结论。

更重要的是，**新增门禁声称检查「逐 ID 的主台账/工作卡状态」，实际只在极窄条件下生效**。`_work_item_problems()` 的判定是：

```python
if f"已交付 {version}" in " | ".join(cells) and status in ("开发中", "未排期"):
    problems.append(...)
```

即只有当主台账状态恰为 `开发中` 或 `未排期`，且发布记录声称已交付时才报错；另外只检查工作卡前 12 行是否出现版本号，不比较表行与工作卡首行的措辞。本机用独立的 `gate_root`（只复制门禁所需 11 个文件，不改动工作区）实跑三组对照：

| 实验 | BUG-119 主台账状态 | `validate_release_records("0.23.1", None, gate_root)` |
| --- | --- | --- |
| A（**发布现状**） | `已有修复但待验收` | **0 problems**（尽管工作卡写「已交付 0.23.1」、发布记录写「已实现并实机验收」） |
| B | 改为 `开发中` | **1 problem**：`BUG-119 claims 已交付 0.23.1 but docs/BACKLOG.md says 开发中` |
| C | 改为 `部分交付，剩余待验收`（仍与工作卡冲突） | **0 problems** |

**结论**：门禁对「占位 / 缺段 / 缺附件名 / 缺摘要」这类硬故障非常有效（第 3.2 节已证），但对「状态措辞不一致」这一 0.23.0 反馈的核心诉求，覆盖面不足。本实验不是否定门禁，而是指出它的逐 ID 子检查目前是「条件式」而非「一致性」检查。

**建议**：把 `_work_item_problems()` 改为比较「主台账状态 / 目标版本」与「工作卡首行交付结论」「逐 ID 表技术状态」是否落在同一状态枚举（例如 `已交付 / 部分交付（列明剩余）/ 开发中 / 未排期`），任一不一致即返回 problem；若确需保留保守措辞，则在逐 ID 表中增设「差异说明」列并要求填写理由，避免静默通过。同时把 FEAT-066 这类历史卡纳入一次全表扫描，而不只扫本版发布记录表里的 3 个 ID。
