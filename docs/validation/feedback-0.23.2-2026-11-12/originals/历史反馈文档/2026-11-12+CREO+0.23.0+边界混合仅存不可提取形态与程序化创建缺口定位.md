# 2026-11-12 + CREO + 0.23.0 + 边界混合仅存"不可提取"形态：程序化创建的真正缺口已定位

> 反馈对象：MCP_CREO_MechDog 作者
> 版本：`server_version = 0.23.0`（用户正式升级版），原生 `creo_worker.exe` 为**本地诊断构建**（详见第 7 节）
> 宿主：Creo Parametric **10.0.0.0**，`creo_release_numeric = 42`；作者基线 Creo 12.4.0.0（`44`）
> 模型：`bulb_l030`（`806b9d5336354515986d9776bafff46f`），rev4，mm，SEC_A=40 / SEC_B=48 / SIDE_NURBS=54
> 关系：本文**取代** `2026-11-12+CREO+0.23.0+门禁已修但Creo10不支持元素树回读致放样回滚.md` 中"回滚原因"的定性，并把"是否还有别的路"从推测变成实测

---

## 1. 结论先行

上一轮我给出的判断是"程序化创建这条路封死了"。**这个措辞是错的，本轮用五组实机实验把它换成了更准确的三句话**：

1. **内核确实完全支持，且确实接受程序化建出的边界混合树。** `PRO_E_FEATURE_FORM = PRO_USE_SURFS` + `PRO_E_DTM_SRF_TYPE = 11` + `PRO_E_BNBLN_*` 子树，`ProFeatureWithoptionsCreate` 返回 `0`，特征被真实创建（id 62 / 64 …），状态 `PRO_FEAT_ACTIVE`。
2. **但它只有"带缺失创建"这一种形态可用，而这一形态没有任何补全途径。** 该特征恒为 `ProFeatureIsIncomplete = true`，几何项 `0`、面 `0`、quilt `0`；`ProFeatureElemtreeExtract` 与已废弃的 `ProFeatureElemtreeCreate` **同时**返回 `-18 (PRO_TK_INVALID_TYPE)`。原设计"不完整创建 → 提取 → 补全 → redefinе"的闭环在 Creo 10 上**缺了中间那一环**。
3. **决定这一点的不是 `PRO_E_FEATURE_FORM` 的取值，而是它选中的子类型。** 12 个 `ProFeatFormType` 值全扫：**只有 512 保留 `PRO_E_BNBLN_CURVES` 子树，而 512 恰好就是 Creo 10 唯一拒绝提取的那一个**。可提取的三个（1024 / 262144 / 2097152）都是把 BNBLN 子树**丢弃**后当成别的曲面类型建的。

**所以正确的表述是：不是"没有 API"，而是"Creo 10 没有给出拼出完整树的任何途径"。** 这一点是可以被作者直接修掉的（见第 5 节）。

## 2. 实验矩阵（全部为本机实测，非推断）

### 实验 1 — 创建选项 × FORM 值

| `PRO_E_FEATURE_FORM` | 名称 | 写 DTM_SRF_TYPE | `create_code` | `extract_code` | 几何项 |
|---|---|---|---|---|---|
| 省略该元素 | — | 是 | **-1** | — | — |
| 0 | `PRO_NOTYPE` | 是 | **-1** | — | — |
| 8 | `PRO_BLEND` | 是 | **-1** | — | — |
| 128 | `PRO_THIN` | 是 | **-1** | — | — |
| **512** | **`PRO_USE_SURFS`** | 是 | **0** | **-18** | **0** |
| **512** | `PRO_USE_SURFS` | **否** | **-1** | — | — |
| 1024 | `PRO_FLAT` | 是 | 0 | **0** | 0 |
| 4096 | `PRO_COPY` | 是 | **-2** | — | — |
| 16384 | `PRO_ADV_SURF` | 是 | **-1** | — | — |
| 16384 | `PRO_ADV_SURF` | 否 | **-1** | — | — |
| 262144 | `PRO_SHUT` | 是 | 0 | 0 | 0 |
| 524288 | `PRO_SKIRT_EXT` | 是 | **-2** | — | — |
| 1048576 | `PRO_SKIRT_FILL` | 是 | **-2** | — | — |
| 2097152 | `PRO_PRTSPLIT` | 是 | 0 | 0 | 0 |

三条可以当场落地的结论：

- **`PRO_E_DTM_SRF_TYPE` 是必填的。** 512 带它 → `0`；512 不带它 → `-1`。这条元素不能省。`-1` 全程 `element_errors.total = 0`，内核拒绝但不归因。
- **`PRO_ADV_SURF (1<<14)` 不是边界混合的 form。** 这是我在上一轮唯一提出的具体假设（"高级曲面用 `PRO_ADV_SURF`"），本轮已实测否定，两个变体都是 `-1`。
- **`-18` 只出现在 512。** 这是"BNBLN 子树被真正当作边界混合处理"的唯一指纹。

### 实验 2 — 对已建成的 512 特征再读一次树

```
ProFeatureElemtreeExtract(&f, nullptr, PRO_FEAT_EXTRACT_NO_OPTS, &tree) = -18
ProFeatureElemtreeCreate(&f, &tree)                                       = -18   ← WF5 前的老接口，同结果
ProElemtreeVerify((ProSolid)board, nullptr, root)                         = -2    ← PRO_TK_BAD_INPUTS
ProElementDiagnosticsCollect(...) 逐元素                                  = 0 条
```

- 两个提取器都拒绝 → 没有任何"已建成的树"可读。
- `ProElemtreeVerify` 在 Creo 10 上**传 NULL 路径直接 `PRO_TK_BAD_INPUTS`**，文档承诺的"创建前校验树"不可用；诊断因此恒为空（诊断只由 verify 挂上去）。

### 实验 3 — 补入 SDK 声明过、`surface_loft` 从未写的元素（14 组）

把 `ProElemId.h` 里全部边界混合元素按以下维度逐组补入并记录每组的元素写入结果：

`PRO_E_BLEND_TYPE(646)` ∈ {0,1,2}、`PRO_E_CTRL_TYPE(639)` ∈ {0,1}、`PRO_E_BBL_APPENDIX(3170)`、`PRO_E_CTRL_PTS(662)`、`PRO_E_REFERENCE_CURVES(649)`、`PRO_E_CHAIN_CURVES(650)`、`PRO_E_BNBLN_ADVANCED(469)`、`PRO_E_BNBLN_TAN_COND(459)`，以及"全部同时加"。

结果：**14 组全部 `create_code = -1`**（`NO_OPTS`），只有 `INCOMPLETE` 控制组返回 `0`。

顺带测出两条常量类型事实（对作者有用）：

- `PRO_E_BLEND_TYPE`、`PRO_E_CTRL_TYPE`、`PRO_E_BBL_ADD_CLOSED`、`PRO_E_BNBLN_RULED` 都是**整型**元素（写入成功）。
- **`PRO_E_BNBLN_TAN_COND` 不是整型元素**：`ProElementIntegerSet` 返回 `-18`。`native/surface_loft.cpp` 的 `surface_loft_apply_conditions` 走的是"提取后补写"路径，一旦提取不可用，这条路径在 Creo 10 上根本无法被验证。

### 实验 4 — 元素顺序（4 种布局）

`NAME` 在曲线前 / 在曲线后 / 完全不写 / `PRO_E_DTM_SRF_TYPE` 移到曲线之后。**四种布局全部 `-1`。**

### 实验 5 — 判据自检（本轮最重要的一步）

实验 3、4 都建立在"`NO_OPTS` 返回 `-1` ⇒ 树缺必填元素"这个前提上。**这个前提不成立，我在此更正：**

同一个 `PRO_FLAT(1024)` 树：

- `INCOMPLETE` → `create_code = 0`，且**可提取**（29 个元素，是一棵真实的平面数据面树：`PRO_E_STD_SECTION` / `PRO_E_STD_SEC_SETUP_PLANE` / `PRO_E_SKETCHER`，`PRO_E_BNBLN_CURVES` 被丢弃）
- `NO_OPTS` → `create_code = -1`

**即：`PRO_FEAT_CR_NO_OPTS` 在 Creo 10 上对数据面类特征恒为 `-1`，与树是否完整无关。** 所以实验 3 的"全 -1"**不能**用来证明"缺元素"。我把这条列为本文最主要的 caveat，并且不据此下结论。

## 3. 真正被证实的缺口

把上面五组实验收拢，只剩一条结论是硬的：

```
Creo 10 上，边界混合的唯一可用形态（FORM=512）
  ├─ 创建：只能以 INCOMPLETE 建成空壳（几何 0 / quilt 0）
  ├─ 提取：-18（两个提取器都拒）
  ├─ 校验：-2（ProElemtreeVerify 不可用）
  └─ 因此：不完整 → 提取 → 补全 → redefine 的闭环在中间断开
```

而作者基线 Creo 12.4 上 FEAT-065 是 live-verified 通过的，说明**在 12.4 上提取这一环是通的**。缺口是版本行为差异，不是设计错误。

**一个模型层面的旁证**：用户在本机 GUI 里手工建的边界混合（`bulb_guide_0200`，feature `101`）用同一接口读取，同样是 `-18`。所以这不是"MCP 建的树不合法"，而是"这一类特征在 Creo 10 上一律不可提取"，GUI 建的也一样。

## 4. 对 `surface_loft` 的三条具体修正建议

| # | 位置 | 现状 | 建议 |
|---|---|---|---|
| A | `surface_loft.cpp` 建树 | 固定 `PRO_E_FEATURE_FORM = PRO_USE_SURFS` | **保留 512**（实测这是唯一正确值），但把"只有 512 可建、且 512 不可提取"写进注释，避免后来者再走 `PRO_ADV_SURF` 的弯路（我走过，已否定） |
| B | 提取失败分支 | 降级为 `verification = "geometry_only"` 并继续 | **改为在建树前先探测一次能力**：对一个已知合法的最小边界混合树做 `Extract` 试探，失败即**在任何特征创建之前**返回明确错误 `SURFACE_LOFT_EXTRACT_UNSUPPORTED`，而不是先建一个空壳再回滚。当前行为会让每次调用都留下一个"建了又删"的特征（见第 7 节），对模型无关但日志噪声很大 |
| C | 能力声明 | `surface_loft` 在 Creo 10 上 `available = true / state = "compiled"` | 增加 `release_capability` 一项：`element_tree_extract = false`，并在 `creo_capabilities` 里如实反映"该宿主无法完成边界混合"，让客户端能在**提交前**知道，而不是等回滚 |

## 5. 给作者的"如何真正闭环"（按可行性排序）

1. **最强、最省事：由作者在 Creo 12 上导出一次模板 XML。**
   `ProElemtreeWrite(tree, PRO_ELEMTREE_XML, path)` 在 12.4 上能对边界混合成功（提取在那边通），把导出的 XML 作为模板随包发布。低版本用户用 `ProElemtreeFromXMLCreate` 读入，只替换 `PRO_E_STD_CURVE_COLLECTION_APPL` 里的曲线引用，再 `ProFeatureWithoptionsCreate`。**这条路完全绕开提取**，因为树是"外部给的完整树"，不需要内核补全。本机已验证 `ProElemtreeFromXMLCreate` / `ProElemtreeWrite` 的声明在 Creo 10 SDk 中存在（`ProElement.h:3166 / 3207`），只是缺一棵正确的树。
2. **次强：在 Creo 10 上改用"先建后改"以外的入口。** 例如同一几何改用 `PRO_FEAT_DATUM_QUILT(946)` 承载，或在 `PRO_E_DTM_SRF_TYPE` 之外寻找 512 的可提取变体 —— 这需要作者在 12.4 上 dump 出真实树后逐个元素比对，MCP 侧无法独立完成。
3. **兜底：在能力表里显式标注不支持**，并给出"用精确 NURBS 曲面导入"的替代说明（数学上与 TXT 附录 B030 的 Surface-Loft2 等价，不是近似）。本条不改变内核限制，但能让客户端不误判。

## 6. 仍未解决 / 未验证

- **空壳特征的"缺哪个元素"始终没有被内核告知过。** 四次实验里 `element_errors.total` 恒为 0，`ProElemtreeVerify` 不可用，诊断恒空。要拿到这份清单，只能按第 5 节第 1 条从 12.4 导模板比对。
- **`PRO_E_BNBLN_TAN_COND` 的正确数据类型/父级未确定**（本轮只测出"整型写法返回 -18"）。
- 本文全部结论限于 **Creo 10.0.0.0**，不外推到 Creo 11/12。
- 实验 3、4 的负结果**不构成"补这些元素无效"的结论**（判据已自证失效，见 2.5）。

## 7. 本机当前状态（必须登记）

原生 worker 现为**本地诊断构建**，不是 0.23.0 官方产物：

- `native/surface_loft.cpp` `sha256 = cc164b9a…`（后续轮次又有改动，最终以 `build/creo_worker.exe` 为准）
- 备份：`native/surface_loft.cpp.bak-0.23.0-20261112-140834`
- 该诊断构建把 `surface_loft` 改造成**多候选探针**：一次调用会按候选表依次建特征、判定、再删除（最多 9 个候选）。**它不改变模型最终状态**（全部失败即整体回滚，`rollback_succeeded = true` 已逐次确认），但绝不应当作生产构建使用。
- 若要恢复官方行为：把 `native/surface_loft.cpp` 换回上述备份后 `python bridge.py build` 即可（worker 每作业新起进程，无需重启 MCP 客户端）。
