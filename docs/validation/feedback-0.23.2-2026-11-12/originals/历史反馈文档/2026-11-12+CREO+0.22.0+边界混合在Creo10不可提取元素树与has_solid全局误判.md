## 一、结论先行（含对前两轮反馈的自我更正）

### 1.1 我要更正前两轮的结论

11-11 与 11-12 两份反馈里，我把 `Probbl.h` 门禁定性为**「误剔」**，理由是「Creo 10 元素树常量完备，
只要补一个 `#define` 就能编进去」。**这个定性是错的**，本轮拿到了三条彼此独立的硬证据：

| # | 证据 | 结论 |
|---|---|---|
| 1 | 门禁块内 **115 个** PTC 符号全量比对 Creo 10 SDK，**缺 1 个**：`PRO_E_DTM_SRF_TYPE_BND_BLEND` | 前两轮「只依赖 5 个 `PRO_E_BNBLN_*`、常量完备」的说法**漏算**了它 |
| 2 | `ProFeatureElemtreeExtract` 对**用户在 GUI 手工建的边界混合特征**返回 `-18 = PRO_TK_INVALID_TYPE`；Creo 10 官方文档对该码的释义是 **"Extraction of the element tree is not supported for this feature type"** | Creo 10 的 Toolkit **根本不提供边界混合的元素树**，不只是缺一个常量 |
| 3 | Creo 10 Toolkit 的 415 个头文件里**没有任何边界混合头**（`ProFlatSrf.h` / `ProSurfReg.h` / `ProSurface.h` 有，`ProBndBlend.h` 之类没有）；`PRO_E_DTM_SRF_TYPE` 只出现在 `ProElemId.h` / `ProSmtDrvSurf.h` / `ProSmtShell.h`，后两者都是**钣金** | 边界混合不是 Creo 10 Toolkit 的公开建模路径 |

**因此：作者给 `surface_loft` 加门禁是有正当理由的，方向正确。**我之前说「这是误判、补个 `#define` 就好」
会误导作者去做一件在 Creo 10 上注定失败的事——**补了 `#define` 能编译通过，但 Creo 10 内核不会认这个元素树，
而且因为提取本身就是 INVALID_TYPE，连"是否真的建成了"都无法验证**。这一点比编译失败更危险。

### 1.2 但门禁的**机理与报文**仍然是错的

虽然「关掉门禁」不可行，门禁本身仍有两处需要改：

- 判定依据用 `__has_include(<Probbl.h>)` 表达了一个**头文件存在性**问题，实际根因是
  **Creo 版本级能力缺失**。同一份 Creo 10 SDK 上，头文件永远不会出现，这个判断等价于写死，但报文会
  让人以为是「装错 SDK 了，换 SDK 就行」。
- `state="sdk_header_missing"` 的报文只说缺 `Probbl.h`，没有说明「**该 Creo 版本不支持边界混合元素树**，
  补头文件也无效」。作者自己的 `known_limitations` 里那条 `creo9_10_unverified`
  （"do not infer Creo 9/10 support from Creo 12.4 results"）表达的才是真实情况，但两个字段没有互相引用。

### 1.3 `has_solid` 全局误判仍然成立（P2 不变）

`native/surface_loft.cpp:1073/1101` 用「操作后整个模型是否 has_solid」判断「本次是否创建了实体」，
在已有实体的模型上必然误判。0.22.0 源码该处未变。这一条与 §1.1 无关，**独立成立、可独立修**。

### 1.4 顺带发现：0.23.0 已发布

`creo_capabilities.update` 本轮返回 `update_available`，`latest_version=0.23.0`
（`https://github.com/wudahua/MCP_CREO_MechDog/releases/tag/v0.23.0`）。
本文所有结论均基于 **0.22.0**。

## 二、零风险取证实验（本轮新增的关键证据链）

用户的诉求是「不要近似方法」。在门禁挡住 `surface_loft` 的情况下，我设计了一个**不改代码、不重启 MCP、
不重启 Creo** 的零风险取证方案：请用户在 Creo 界面**手工**建一个边界混合曲面，再用 MCP 的
`creo_dump_feature_tree` 把它的元素树导出来，直接读出 `PRO_E_DTM_SRF_TYPE` 的真值。

### 2.1 用户手工建成的特征

在隔离试验模型 `bulb_guide_0200` 中，用户选中已有的两条真实导线草图
`SIDE_GUIDE`(id 42) 与 `SECTION_X64`(id 50)，用默认参数完成一次边界混合，并保存。

`creo_refresh_model`（job `db43650f51194276a9b81ba06a2c52b6`，live_query）实测：

| 项 | 建之前 | 建之后 |
|---|---|---|
| features | 14 | **15** |
| quilts | 1 | **2** |
| 新增特征 | — | **id=101**，`type=942`=`PRO_FEAT_DATUM_SURF`（`ProFeatType.h:44`），`parents=[42,50]`，`children=[]` |
| 新增 quilt | — | `area_mm2=262784.3451752057`，`bbox=[[6409.37,-0.1,-660.1],[7809.57,181.83,-459.9]]`，`closed=false` |

**这本身就否定了「Creo 10 建不出边界混合」的可能**：内核完全支持，用户一次就建成了，
面积与包围盒都是真实几何。所以问题不在内核，也不在环境，而在 **Toolkit 侧的元素树接口**。

### 2.2 取证失败：元素树提取被 SDK 拒绝

```
creo_dump_feature_tree(model_id=f24256bc…, feature=101)
→ job 20170dd0431a42f086a59ec32d14ac31
→ status=failed, stage=execute_dump_tree
→ Toolkit call ProFeatureElemtreeExtract(&f, nullptr, PRO_FEAT_EXTRACT_NO_OPTS, &root)
   failed with code -18
```

`-18` 的准确定义（`ProToolkitErrors.h:30`）：

```c
PRO_TK_INVALID_TYPE = -18,
```

Creo 10 官方 API 文档 `protkdoc/api/1422.html`（`ProFeatureElemtreeExtract`）对该返回值的原文：

> `PRO_TK_INVALID_TYPE` — **Extraction of the element tree is not supported for this feature type.**

即：**Creo 10 明确不支持对「边界混合特征」这一 feature type 做元素树提取。**

### 2.3 对照实验：证明不是 MCP 的 bug

为排除「`creo_dump_feature_tree` 在 Creo 10 上整体不可用」，做了两组对照：

| 目标 | 特征类型 | 结果 |
|---|---|---|
| `feature=56` `FILL_RECT` | `949` = `PRO_FEAT_CURVE` | ✅ `succeeded`，写出 `feature_56.xml`（job `7bac5108dee84e7dbdfb0d4982d7699b`） |
| `feature=65` `QUILT_PROBE` | `942` = `PRO_FEAT_DATUM_SURF` | ✅ `succeeded`，写出 `feature_65.xml`（job `2593339f5d1440a88a27b09321947ed3`） |
| `feature=101` 边界混合 | `942` = `PRO_FEAT_DATUM_SURF` | ❌ `-18 PRO_TK_INVALID_TYPE` |

**关键**：65 与 101 的 `PRO_FEAT_*` 类型**完全相同**（都是 942 数据面），却一个能导一个不能。
所以 `-18` 不是"数据面类型不支持"，而是**数据面下「边界混合」这个子类不支持**；
工具本身、连接、模型状态全部正常。

## 三、即使用户手工建成了特征，也拿不到枚举真值——为什么

我原本的计划是：拿到真值 → 用 `creo_create_feature_tree` 传裸整数建特征（该工具接受 `{"id":1131,"integer":<值>}`），
**绕开 C++ 编译和 MCP 重启**。这条路在 §2.2 处断了，且没有替代方案：

| 想过的取真值途径 | 结果 |
|---|---|
| `dump_feature_tree` 导元素树 | ❌ §2.2，`PRO_TK_INVALID_TYPE` |
| `creo_lookup_constants(prefix="PRO_E_DTM_SRF")` | 只返回元素 ID `PRO_E_DTM_SRF_TYPE=1131`，**不含枚举取值名** |
| 遍历 Creo 10 SDK 全部头文件的 `PRO_DTM_SRF*` | 只有 3 个，且全是钣金：`AS_WALL=15` / `AS_WALL_SHELL=24` / `EMPTY_BODY_CONV=93` |
| `protkdoc` 离线文档 | 无 `PRO_E_DTM_SRF_TYPE_BND_BLEND` 任何记载 |
| 从 `.prt` 二进制反推 | 不可行 |
| Creo trail 文件 | 只记录菜单动作，不记录元素树枚举 |

**结论**：在 Creo 10 上，`PRO_E_DTM_SRF_TYPE_BND_BLEND` 的真值**无法通过任何本机手段获得**。
前两轮反馈里「我先取证再打补丁」的计划，本轮证明在 Creo 10 上**不成立**。

## 四、`PRO_E_DTM_SRF_TYPE` 在 Creo 10 里到底是谁——一个可能的额外坑

`feature_65.xml`（用户能正常导出的平面填充面）的完整树里，**根本没有 `PRO_E_DTM_SRF_TYPE` 这个元素**：

```xml
<PRO_E_FEATURE_TREE AppVersion="10.0" type="compound">
  <PRO_E_FEATURE_TYPE type="int">PRO_FEAT_DATUM_SURF</PRO_E_FEATURE_TYPE>
  <PRO_E_FEATURE_FORM type="int">PRO_FLAT</PRO_E_FEATURE_FORM>
  <PRO_E_STD_SECTION type="compound">
    <PRO_E_STD_SEC_METHOD type="int">0</PRO_E_STD_SEC_METHOD>
    <PRO_E_SEC_USE_SKETCH type="selection">…ref id=56…</PRO_E_SEC_USE_SKETCH>
    …
  </PRO_E_STD_SECTION>
  <PRO_E_STD_FEATURE_NAME type="wstring">QUILT_PROBE</PRO_E_STD_FEATURE_NAME>
  …
</PRO_E_FEATURE_TREE>
```

Creo 10 里数据面的「子类型」是靠 **`PRO_E_FEATURE_FORM`** 选的：

```c
// ProFeatForm.h
PRO_EXTRUDE   = 1,  PRO_REVOLVE = 2,  PRO_SWEEP = 4,  PRO_BLEND = 8,
PRO_THIN      = 128, PRO_USE_SURFS = 512, PRO_FLAT = 1024, PRO_COPY = 4096,
PRO_ADV_SURF  = 1<<14,   // ← 高级曲面
PRO_SHUT / PRO_SKIRT_EXT / PRO_SKIRT_FILL / PRO_PRTSPLIT …
```

而 `PRO_E_DTM_SRF_TYPE` 在 Creo 10 里的官方归属是**钣金**：

```c
// ProSmtDrvSurf.h  Note 2.
//   PRO_E_DTM_SRF_TYPE must be of PRO_DTM_SRF_AS_WALL type
typedef enum Pro_Smt_DtmSrf_Type {
  PRO_DTM_SRF_AS_WALL = 15, PRO_DTM_SRF_AS_WALL_SHELL = 24, PRO_DTM_SRF_EMPTY_BODY_CONV = 93
} ProSmtDtmSrfType;

// ProSmtShell.h
//   PRO_E_DTM_SRF_TYPE must be of PRO_DTM_SRF_AS_WALL_SHELL type
```

而 `native/surface_loft.cpp:918–924` 的构造是：

```cpp
integer(root, PRO_E_FEATURE_TYPE, PRO_FEAT_DATUM_SURF);
integer(root, PRO_E_FEATURE_FORM, PRO_USE_SURFS);                 // 512
integer(root, PRO_E_DTM_SRF_TYPE, PRO_E_DTM_SRF_TYPE_BND_BLEND);  // ← Creo10 无此符号，且该元素是钣金用途
```

**需要作者确认的问题**：在 Creo 12.4 上，边界混合到底是用
`PRO_E_DTM_SRF_TYPE = <BND_BLEND>` 选的，还是应该用 `PRO_E_FEATURE_FORM = PRO_ADV_SURF` 选的？
如果是后者，那么在 Creo 12 上可能也存在树结构隐患，只是被别的条件掩盖了。
（本文只能证明 Creo 10 的情况，无法验证 Creo 12，故仅提出疑点，不下结论。）

## 五、`has_solid` 全局误判（P2，独立成立，可直接修）

`native/surface_loft.cpp` 在放样成功后做结果校验：

```cpp
// 第 1073 行
details["has_solid"] = inspection(false)["has_solid"];      // ← 整个模型的全局状态
// 第 1101 行
if (details["has_solid"].get<bool>())
    throw std::runtime_error("surface_loft created solid material; a surface loft must not");
```

`inspection(false)` 查的是**操作后整个模型**是否有实体，而不是「本次操作是否新增了实体」。
只要模型原本就有任何实体（例如护卫舰船体主模型 `frigate_txt_rebuild`，`has_solid=true`），
无论放样是否只生成开放 quilt，`has_solid` 恒为 true → 必然抛错并回滚。

这正好解释 release notes 里「已有实体模型中 `surface_loft` 一律失败（原生 `has_solid` 看整个模型）」，
但它是 **MCP 侧把全局状态当增量**，不是 Creo 内核的限制。

**修复建议**：创建特征前先取 `pre = inspection(false)["has_solid"]`，
仅在 `!pre && post` 时判定为「创建了实体」；或比较 `volume_mm3` / `bodies.with_material` 的增量。

> 证据边界：本条来自 0.22.0 源码静态分析 + release notes 自述现象互证。
> 因门禁未开，本机无法真机触发，**不宣称已在 Creo 10 上跑出该错误**。

## 六、作者已有的正确方向：GUI 编排回调（建议扩展）

我读了 `native/blend_create.cpp`，它的第一行注释就是这个项目在 Creo 10 上的**正解**：

```cpp
// Creo 10 ordinary Blend: asynchronous orchestration with a small synchronous
// external-selection callback. All references are resolved before the dashboard.
```

也就是说，作者对 **普通混合（ordinary Blend）** 已经采用了「**不碰元素树，改为编排 Creo 自己的建模面板**」
的方案——因为 Creo 10 同样没有 Blend 的元素树头文件。这个架构恰好绕开了本文 §2–§4 的全部障碍。

当前回调状态（`creo_callback_status`，本轮实测）：

| 项 | 值 |
|---|---|
| `readiness` | **`not_loaded`** |
| `registration_status` | `unknown` |
| `protocol` / `contract` | `3` / `blend-selection-v3-ordered-curves-mm` |
| `next_action` | `start_or_register_application_manually` |
| `artifact_status` | `prepared`（loader/callback DLL 均已部署，SHA256 齐全） |

**但这条通道目前只能产出实体普通混合**：`creo_loft` 的工具描述明确
"Cut, **surface** and new_body are rejected"；`creo_new_loft_part`（seed 路线）同样只能出实体，
且明确 "No existing-target insertion, cut/surface modes"。

**因此给作者的核心建议**：把已经验证过的「GUI 编排 + 选择回调」架构，从**普通混合面板**

而且它天然支持 `sections` + `guides` + 收敛点，正是球鼻艏需要的。

## 七、顺带发现：手工保存后托管模型进入「半脱管」且无公开恢复路径

用户按指引在 GUI 里建特征并 `Ctrl+S` 后：

| 观察点 | 值 |
|---|---|
| Creo 会话里 `BULB_GUIDE_0200` 的 origin | `…\output\bulb_guide_0200.prt.8` |
| `creo_list_session_models` 该条的 `model_id` | **`null`**（已被判定为"非托管"） |
| `creo_list_models` 该模型的 `part_file` / `sha256` / `revision` | 仍是 `…prt.6` / `10e2e3fd…` / `5`（**未察觉外部保存**） |

即：**用户手工编辑并保存一个受管模型后，MCP 记录仍指向旧版本文件，而会话模型已被判定为未托管。**
`creo_reconcile_model` 的适用范围是 `status=failed` / 异常状态，**不覆盖「状态 ready 但被外部改过」这种情况**，
`capabilities.support_status` 也没有对应条目。这会让任何"手工配合 MCP"的调试流程留下状态分叉。

## 九、给作者的需求清单（按优先级）

1. **【P1/P3】重写门禁语义**：保留门禁，但把判定从 `__has_include(<Probbl.h>)` 改为
   **版本/能力判定**，并在 `worker_build_identity.features.surface_loft` 里新增字段：
   ```
   state: "release_capability_missing"
   reason: "Creo <版本> 的 Pro/TOOLKIT 不支持边界混合元素树提取（ProFeatureElemtreeExtract → PRO_TK_INVALID_TYPE）"
   missing_sdk_requirements: []            // 明确不是缺头文件
   guidance: "补头文件无效；请改用 GUI 编排回调路线或升级 Creo"
   ```
   同时让 `known_limitations` 里的 `surface_loft_sdk_header` 与 `creo9_10_unverified` 互相引用。

2. **【P7 / 核心需求】把 GUI 编排回调扩展到边界混合面板**。
   作者已在 `native/blend_create.cpp` 用「异步编排 Creo 混合面板 + 同步外部选择回调」
   解决了 Creo 10 没有 Blend 元素树的问题；同一架构用于边界混合面板，即可在 Creo 10 上
   **精确**产出 `边界混合(sections + guides + 收敛点 + smooth)`，无需任何 Creo 12 SDK 符号。
   这是球鼻艏这类「3 截面 + 3 导线 + 尖点」曲面的唯一非近似路径。

3. **【P2】修 `has_solid` 校验**：改为操作前后增量（或 volume / bodies.with_material 增量），
   并补一条「已有实体模型内放样成功」的实机用例。

4. **【P4】确认边界混合的选型元素**：Creo 12 上到底是
   `PRO_E_DTM_SRF_TYPE = BND_BLEND` 还是 `PRO_E_FEATURE_FORM = PRO_ADV_SURF`？
   Creo 10 的平面数据面树里不含 `PRO_E_DTM_SRF_TYPE`，请核对两版本差异。

   `PRO_TK_INVALID_TYPE` → `element_tree_unsupported_for_feature_type`，

   `creo_adopt_current_model(mode=inspect)` 能识别并提示「会话文件已是 prt.N+1」。

7. **允许 `surface_loft` 接受任意正交平面截面**（YZ@X、XZ@Y）。

8. **`sketch spline` 暴露 knots/weights/degree**；`dimensioning="coordinates"` 支持 spline。
