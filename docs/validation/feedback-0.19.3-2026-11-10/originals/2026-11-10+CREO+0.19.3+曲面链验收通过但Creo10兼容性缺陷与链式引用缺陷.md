## 二、逐项问题

### P12 `creo_surface_loft` 在 Creo 10 SDK 构建下被编译剔除，提交前拒绝（高，阻断导线曲面）

**实测**：提交 `{"op":"surface_loft","label":"sl_test","sections":["loftc1","loftc2"]}`（两个 YZ 圆截面草图已预先成功创建），直接报错：

```
surface_loft is compiled out of the current worker: its Toolkit SDK is missing Probbl.h
(worker source_digest=3e8a0025…, state=sdk_header_missing). No native job was queued.
```

`creo_session_status.worker_build_identity` 与 `capabilities.families.surface_loft` 一致自报：
`available=false, state="sdk_header_missing", sdk_requirements=["Probbl.h"]`，
`enabled_semantics: "compiled out of the current worker"`。

**评价**：报错本身是**优秀实践**——拒绝发生在 job 排队前、错误点名缺什么头文件、给出 worker digest，比上一版（文档写可用但实际走不通）进步巨大。known_limitations 也如实登记 `surface_loft_sdk_header`。

**给作者的建议**：
1. Creo 10.0.0.0 的 Toolkit SDK 确实不带 `Probbl.h`（边界混合树头文件）。若该树在 Creo 10 上有等价入口（如 `ProSurfacedata`/legacy blend tree 常量），建议提供降级实现或在文档中明确"Creo 10 无解"，避免用户反复试。
2. 文档建议把"本机 Creo 版本 → surface_loft 可用性"做成 `creo_capabilities` 的顶层速查字段（现在要拼 worker_build_identity + families + known_limitations 三处才能得出结论）。

### P13 `quilt_merge` 的结果 quilt 无法被后续 merge 引用：`ProFeatureGeomitemVisit -4`（高，阻断多片缝合链）

**实测**（球鼻艏式"三片缝合"链路）：
- 同一 plan 内：`merge1(surf_extrude + capbot_fill)` 成功，紧接着 `merge2(target=merge1 的 label)` 失败：
  `Toolkit call ProFeatureGeomitemVisit(&f, PRO_QUILT, …) failed with code -4 during execute_quilt_merge`
- **跨 plan 复现**：`merge_box1` 单独提交成功（rev 6，`saved_file_reloaded_and_verified=true`），下一个 plan 里
  `merge_box2(target=merge_box1)` 仍报同样 `GeomitemVisit -4`。
- **workaround 实测成立**：target 恒用**原始 quilt label**（merge 是 `result_quilt_source="retrimmed_target_quilt"` 的原地重剪）：
  `merge_box2b(target=surf_extrude, tool=captop_fill)` 成功，随后 `solidify(reference=surf_extrude)` 成功实体化。
  ——即**缝合链必须始终引用第一次 merge 的 target**，且 solidify 也必须引用该原始 label，而不能引用 merge 的 feature label。

**给作者的建议**：
1. 文档（schema 与 capabilities）应明确写"merge 结果没有可引用的 quilt label；链式缝合请持续以原始 target label 为引用"——当前文档只写了 receipt 字段，用户只能靠试错发现。
2. 更好的修复：给 merge 接受上一步 merge 的 feature label 作为 target（把 label 解析到 retrimmed 后的 quilt），或在 receipt 中额外发布可引用的别名。
3. 错误信息建议附上"hint: 引用原始 target label"。

### P14 `project_curve` 在 Creo 10 上 `ProFeatureWithoptionsCreate -1`（中，作者证据均为 Creo 12.4）

**实测**：`source` 为已验证草图内的直线（curve id 265，feature PROJ_SK），`target` 为 surface 拉伸 quilt（id 176，40×20×15 盒的四面壁），方向引用 `dirz_plane`（MCP 建的 +Z 基准面，与源草图法向平行）。源曲线沿 Z 扫掠的柱面与该盒**底缘和顶缘两处相交**，符合文档声明的"multi-branch 拒绝"形态：

```
Toolkit call ProFeatureWithoptionsCreate failed with code -1 during execute_project_curve
```

**评价**：失败前的拒绝链路是好的——`direction_ref={kind:'datum_feature',label:'TOP'}` 时给出"Unknown feature label: TOP; available labels: …"（系统基准面无 MCP label），`{kind:'datum_plane',axis:'z'}` 时给出"must not be {kind:'datum_plane',label:…}…"的明确拒绝。这两条拒绝信息质量很高。

**给作者的建议**：
1. `-1` 失败本身建议像 surface_trim 的 `feature_status=6` 那样，附带"检测到 N 处相交/分支"的实测提示，帮助调用方区分"几何分支问题"与"Creo 10 兼容性问题"。
2. capabilities 里 project_curve 的验证证据均为 Creo 12.4；建议在 known_limitations 的 `creo9_10_unverified` 条目下显式点名 project_curve/quilt_merge 等已实测过 Creo 10 失败差异的操作，方便 Creo 10 用户避坑。

### P15 `quilt_merge` 对"同一平面内共边相邻"的共面 fill 不稳定（低，存在成功/失败双态）

**实测对照**：
- 批次 4（`thicken` 之后紧跟）：`merge(fill_quilt + fill_quilt2)`（两片 800 mm² 共面 fill，沿 X=40 边相邻）→ `ProFeatureWithoptionsCreate -1` 失败。
- 批次 7（干净上下文，同一对 quilt、同一引用方式）：`merge_coplanar` 成功（feature 422）。

失败与成功的差异仅在前置操作上下文（中间隔着一次整批回滚），未再复现定位。样本量小，如实报告为"复现率低的 -1 失败"，暂不作为确定性缺陷；建议作者若复现，可在 receipt 中输出 merge 前两 quilt 的边界接触判定（类似 measure_surface_group 的 seam gap），把"为何内核拒绝"变成可观测数据。

### 旧问题复核（与护卫舰直接相关的两项）

- **P2（两弧 2.78e-08 mm 闭合轮廓）行为变化，内核层面仍未解**：
  草图预检已把 `near_tolerance` 从"拒绝"降级为"风险标志放行"（提示语还引用了 Creo 12.4 成功挤出 8.215e-7 mm 间隙的证据）——这个改动方向正确。
  但本机 Creo 10 内核仍不焊接该间隙：拉伸 `ARC_TEST_EX` 再生失败 `status=6`，整批回滚（job `b33bf663…`）。
  即：**P2 在 API 层已缓解、在 Creo 10 内核层仍成立**。建议：失败信息中引用该提示已有的证据（"Creo 12.4 可焊、本机 Creo 10 内核实测不焊"），并给出"写死公共端点"或"polyline 采样"的一键 remediation。
- **P1（Blend callback 需手工注册）现状不变**：`creo_callback_status = not_loaded`，`next_action="start_or_register_application_manually"`。实体放样在无人值守场景仍不可用（本次用 surface+solidify 链可部分替代，见第一节）。
