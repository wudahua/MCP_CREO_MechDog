## 2. 问题明细

### P1-1｜`C1083` 已修，但 `surface_boundary_fill.cpp` 的跨文件符号依赖继续阻断 Creo 10 整包编译

**实测（官方 0.19.3 源码包，未打任何补丁，`bridge.py build`）**：

```
RuntimeError: Native build failed (2)
SDK version hint: PRO_E_DTM_SRF_TYPE_BND_BLEND may require a newer Creo Toolkit SDK;
                  the local SDK version may be too old.
native\surface_boundary_fill.cpp(115): error C2065: 'SURFACE_LOFT_TREE_SAMPLE_LIMIT': undeclared identifier
native\surface_boundary_fill.cpp(116): error C2065: 'SURFACE_LOFT_TREE_SAMPLE_LIMIT': undeclared identifier
native\surface_boundary_fill.cpp(118): error C3861: 'loft_element_json': identifier not found
native\surface_boundary_fill.cpp(119): error C2065: 'SURFACE_LOFT_TREE_SAMPLE_LIMIT': undeclared identifier
native\surface_boundary_fill.cpp(158): error C2065: 'PRO_E_DTM_SRF_TYPE_BND_BLEND': undeclared identifier
```

**根因链**：

1. 官方 0.19.2 起在 `native/surface_loft.cpp` 头部加了 `MECHDOG_HAS_PROBBL_HEADER`（`__has_include(<Probbl.h>)`），并把 `#include <Probbl.h>` 放进 `#if MECHDOG_HAS_PROBBL_HEADER`。本轮实测 `C1083=0`，这一步**确实修好了** 0.18.3/0.18.4/0.19.0 连续三版的硬包含问题，值得肯定。
2. 但同一个 `#if` 同时把 `SURFACE_LOFT_TREE_SAMPLE_LIMIT`、`loft_element_json()`、`loft_tree_json()` 包了进去。缺头 SDK 下整个主体不可见，只剩 `mechdog_surface_loft_sdk_state()` 与抛 `SURFACE_LOFT_SDK_UNAVAILABLE` 的 stub。
3. `native/generic.cpp` 无条件 `#include "surface_loft.cpp"` 后再 `#include "surface_boundary_fill.cpp"`，并在调度里调用 `generic_surface_boundary_fill(op)`。
4. 官方 `surface_boundary_fill.cpp`（本轮保存的 pristine 18,323 B）**自身没有任何 `MECHDOG_HAS_PROBBL_HEADER` 门控**，却在 `boundary_fill_tree_json()` 里引用 `SURFACE_LOFT_TREE_SAMPLE_LIMIT` / `loft_element_json()`，并在 `PRO_E_DTM_SRF_TYPE` 处使用 Probbl 派生常量 `PRO_E_DTM_SRF_TYPE_BND_BLEND`。缺头 SDK 上这些符号全部不存在 → 5 个编译错误，`creo_worker.exe` 无法产出。

**我方确认作者已知此根因，因此本报告不把它当「未知缺陷」，而是补上作者明确说缺少的 Creo 10 SDK 证据**：

- `docs/COMPATIBILITY.md:7`（DEV-080 补充）原文：「缺头 SDK 的整包编译还受 `native/surface_boundary_fill.cpp` 复用 `surface_loft.cpp` 内部符号影响，根因、抽头方案与不依赖 `Probbl.h` 的等价元素树见 DEV-080 H01；需 Creo 10 SDK 编译与实机几何验收，**本机未验**，不据门控夹具外推为通过。」
- `docs/work-items/DEV-080.md:20` 把 H01 列为「抽 `native/element_tree_json.h` 解跨文件符号耦合 + 不依赖 `Probbl.h` 的等价元素树」，依赖「Creo 10 SDK 编译 + 原夹具实机」；`:31` 说明「本机无 Creo 10 SDK，不交付未编译的原生分支」；`:3` 状态仍为「首批离线收口已随 0.19.3 交付；原生/实机 H01—H09 与未编号缺口仍开放」。
- `docs/validation/feedback-0.19.0-2026-11-08/MAPPING.md:31` 同样把 P1-1 记为「保留开放（H01）」。

**因此本项定性为「作者已明确声明延后的交付缺口」**，不是新发现、也不是实现回退。按我方长期口径仍如实记录，并附上可回填数据：**0.19.3 官方分发包在 Creo 10.0.0.0 SDK 上无法编译出 worker；任何 Creo 10 用户升级到 0.19.3 都会遇到与 0.19.0 相同的「必须自行打补丁」局面**，只是错误信息从 `C1083` 变成了 `C2065/C3861`。

**版本沿革（诚实口径）**：本机实测 0.18.3 / 0.18.4 / 0.19.0 为 `C1083`（三个版本）；0.19.3 为 `C2065/C3861`（本轮）。`v0.19.1`、`v0.19.2` **本机未单独覆盖编译**，不宣称其实测结论；但静态比对显示 0.19.2 官方包的 `surface_boundary_fill.cpp` 同样无门控、同样引用上述符号（且 0.19.2 → 0.19.3 的 `native/` 零改动），按静态推断 0.19.2 在缺头 SDK 上也会失败——此为**静态推断，非实测**。

**建议（与作者 H01 方向一致，另附一个更小的最小改动）**：

1. 正解：按 H01 抽 `native/element_tree_json.h`，把 `SURFACE_LOFT_TREE_SAMPLE_LIMIT` / `loft_element_json()` / `loft_tree_json()` 移出 `#if`，让 SDK 无关的元素树 helper 在缺头 SDK 上仍可见；再对 `surface_boundary_fill.cpp` 中真正依赖 Probbl 常量的部分单独门控并给出不可用 stub。
2. 更小的最小改动（本轮本机验证可行，见 §5）：**只改 `surface_boundary_fill.cpp` 一个文件**，把 `boundary_fill_tree_json()` 到 `generic_surface_boundary_fill()` 整体包进 `#if MECHDOG_HAS_PROBBL_HEADER`，缺头分支抛 `SURFACE_BOUNDARY_FILL_SDK_UNAVAILABLE`。这样不动 `surface_loft.cpp`，就不会破坏官方 `test_optional_loft_header.py` 的 `using J = int` 单 TU 夹具。
3. 无论采用哪种，建议把「在缺头 SDK 上编译 `generic.cpp` 聚合 TU」加入 CI（见 P1-2）。

### P1-2｜新增的两项头门控契约测试全绿，却无法拦截 P1-1：覆盖面只到 include 行与单个隔离 TU

| 测试 | 实际检查内容 | 能否发现 P1-1 |

| `test_optional_loft_header.py::test_optional_include_is_gated_in_the_handwritten_source` | 字符串顺序断言 | **不能** |
| `test_surface_boundary_fill_contract.py::test_native_is_dispatched_and_included` | 断言 `generic.cpp` 里**文本上**有 `#include "surface_boundary_fill.cpp"`、`else if (kind == "surface_boundary_fill")`、`generic_surface_boundary_fill(op)` —— 纯文本检查，不编译 | **不能**（甚至会强化「已接线」的错觉） |
