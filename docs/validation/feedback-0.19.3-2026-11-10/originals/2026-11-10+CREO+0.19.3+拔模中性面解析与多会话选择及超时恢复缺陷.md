## 二、逐项复现与证据

### P1 `draft` 的 `neutral_plane` 引用形式语义未区分（附误导性文档示例）

**现象**：对驾驶室（BRIDGE，Z=350~560 的六棱柱体）5 个侧面加 15° 拔模，中性面取底面所在平面。

第一次提交（job `6c794989d4eb46cda455029730bcfb90`）：
```jsonc
{"op":"draft","label":"bridge_draft15","angle":15,
 "surfaces":[{"kind":"surface","id":2507}, ...5 faces...],
 "neutral_plane":{"kind":"datum_plane","axis":"z","offset":350}}
```
排队执行约 2 分钟（大模型完整再生）后失败：
```
Plane reference must identify exactly one surface; inspect the model and use a surface ID
```
原因：Z=350 高度上模型有多张水平面（主舱顶、驾驶室底等），`datum_plane axis+offset` 形式按"平面位置找面"解析到多张面。

第二次提交（job `641c08c7e67a46a6a779b679f4397f46`）仅把 `neutral_plane` 换成：
```jsonc
"neutral_plane":{"kind":"plane","normal":[0,0,1],"offset":350}
```
立即成功（rev10，`effective_flip=true`，拔模几何与 TXT 吻合）。

**问题点**：
1. `creo_capabilities` 的 references.creo_draft 示例恰恰写的是 `{"kind":"datum_plane","axis":"z","offset":0}`——只在空模型/唯一面高度成立，**示例本身会诱导调用方走进本次踩坑**。
2. 两种形式的语义差异（按"基准面特征"解析 vs 按"几何平面位置"解析）在文档任何地方都没有说明。
3. 错误信息 "Plane reference must identify exactly one surface" 不指名是 `neutral_plane` 还是 `surfaces[]` 里的哪个引用失败，也不提示"改用 {kind:'plane',normal,offset} 形式"。

**建议**：
1. references.creo_draft 示例改为 `{kind:'plane',normal:[0,0,1],offset:N}`，并显式注明 "`datum_plane` 形式要求该位置只有一张面，多面环境请用几何平面形式"。
2. 在提交前（或失败信息里）区分两种引用的解析结果；失败信息附带"该高度检测到 N 张候选面"。

### P2 多 Creo 会话 `-36 ambiguous` 没有可执行的程序化选择路径

**现象**：本机同时存在两个 Creo 实例（两个 parametric.exe/xtop.exe 进程对）时，所有工具返回：
```json
{"connected":false,"connection_state":"ambiguous","toolkit_code":-36,
 "message":"Multiple Creo sessions match; configure creo_session_id and retry"}
```

按提示语逐字执行的实际结果：
1. `config.json` 的 `creo_session_id` 在**服务启动时读取**——运行中的服务上编辑配置后重试，`startup.selected_session_configured` 仍为 `false`，连接行为不变（本次实测验证）。
2. 文档与工具集均未说明 `creo_session_id` 应填什么。查源码可知它最终传给 Toolkit `ProEngineerConnect` 的 `proe_session_id` 参数，其格式是 `host:H:addr_ver:A:addr_type:T:rpcnum:R:rpcversion:V:netaddr:N`（来自 `ProEngineerConnectIdExtract`）——这个 ID **没有任何 MCP 工具可以枚举**：`creo_list_session_models` 自身就需要先建立连接，形成死锁。
3. 本次通过 netstat 观察到两个实例分别监听 127.0.0.1:693 与 127.0.0.1:921，理论上可手工拼 ID，但字段枚举值（addr_ver、addr_type、rpcversion）在本机无从确认，构造出的 ID 无法验证——这条路实际不可行。

**最终恢复方式**：由人工关闭多余 Creo 实例 → `creo_startup_status(retry=true)` 自动拉起唯一实例 → 恢复。对无人值守的 MCP 客户端场景，这意味着**多会话状态只能靠人解决**。

**建议**：
1. 提供 `creo_list_creo_sessions` 之类的只读工具：枚举当前机器上所有 Creo 实例及其连接 ID（Toolkit 侧可在无连接状态下通过 `ProEngineerConnectIdExtract` 的变体或进程探测+连接试探获得）。
2. 支持会话级参数：在连接类工具上接受显式 `session_id` 参数（覆盖配置），并把 `config.json` 的读取改为每次探测时热读。
3. `-36` 错误信息应写明："当前无法程序化区分多个会话；请关闭多余 Creo 实例，或在 config.json 配置 creo_session_id 并重启 MCP 服务"——把"需要重启服务"这个关键事实告诉调用方。

### P3 大批次在大型模型上超时进入 `unknown_outcome`，且全程无进度（P6 的加重形态）

**现象**：在 378 特征模型上提交 28 op 批次（job `231457ce3b1a4ef1b22725ce286a67cd`：8 个特征的删除+26 个重建，含嵌套环草图与浅凸拉伸）。轮询记录：
- 执行阶段 `executing_feature_plan` 持续约 25 分钟，`native_progress.log_bytes` 从 3 MB 涨到 16 MB，但 `stages_seen=0`、`reason="no_phase_lines"` **全程不变**；
- 最终 `status="unknown_outcome"`，message 为 "Native worker timed out; inspect Creo and the native checkpoint before retrying"。

而随后 `creo_reconcile_model(inspect, live=true)` 显示：live 模型 healthy、378+ 特征、体积较基线 +29.71×10⁶ mm³，与 28 op 的期望重建量（计算值 ≈30.66×10⁶ mm³，含与既有几何的重叠合并差）吻合——**即全部操作实际已成功执行，只是 verify/save 阶段超时，被标记为未知**。按 recovery 指引 `accept_live` 提交（job `589bc0ef…`）恢复为 rev17，未重放。

**问题点**：
1. 成功的执行被标记为 unknown_outcome，是所有失败形态里代价最高的：调用方必须走完整的 reconcile 检查链才能确认"其实是成功的"。
2. 超时预算与模型规模无关：本模型单次 verify_model_start 曾实测 1118 秒（18 op 批次 job `59d55e1a…`），28 op 批次的执行+验证总时长天然超出超时预算，**这类失败在大型模型上是结构性的、可预期的**，却没有任何提前提示。
3. `no_phase_lines` 让调用方在整个 25 分钟里无法区分"正在推进"和"已经卡死"。

**建议**：
1. 按 `model.features` 数量动态放大超时预算（或提供 `timeout_seconds` 调用参数），至少在 capabilities/execute_plan 文档中给出"特征数 × 预估单特征再生时间"的预算公式。
2. 落实前次 P6 建议的阶段进度输出（index/total、当前 label）；`native_progress` 在大任务上长期 `no_phase_lines` 使它形同虚设。
3. unknown_outcome 恢复流程建议增加一条捷径：reconcile inspect 已经能拿到 live 的完整几何摘要，若 live 体积/特征数与 plan 断言期望一致，可直接提示"执行疑似已完成，建议 accept_live"（本次是我人工做的体积对账）。

### P4 `feature_state delete` 的级联依赖是无标签基准面，targets 合法形态的报错文本不友好

**现象一（依赖级联）**：删除 4 个错误特征+4 个草图（job `76df51a9…`）被拒绝：
```
feature_state targets do not cover every affected dependency; Creo also deleted these features;
list them explicitly (no automatic cascade): [{"feature_id":6823,"label":null,"name":"no_name",
"type_name":"datum_plane"}, ...共 8 个]
```
这些 `no_name` datum_plane 是 MCP 在创建草图时自动生成的草图支撑面，**天生没有 label**，调用方无法预先知道它们的 ID，只能：第一次提交失败 → 从错误信息抄 8 个整数 ID → 追加重提（job `be8ba2f5…` 成功，16 个 tombstone）。依赖列出机制防止误删是好设计，但对"MCP 自己创建的对象"要求调用方显式列出，等于强制每个删除都走两轮。

**现象二（targets 形态报错）**：按直觉用对象形式 `{"kind":"feature","label":"xxx"}` 提交 targets，得到：
```
operations[0].targets[0].function-wrap[_explain_label_pattern()]: Input should be a valid string
operations[0].targets[0].int: Input should be a valid integer
```
——既没有说明合法形态（裸字符串 label 或整数 ID 的**数组**），又暴露了内部校验器名。第二次才试出正确形态。

**建议**：
1. 对 MCP 自动创建且无 label 的支撑基准面：提供 `"include_auto_datums": true` 之类的开关让删除自动包含，或在文档中写明"删除草图特征时其自动基准面会级联，需一并列出，ID 见首次失败的返回"。
2. schema 校验错误改为面向调用方的文本："targets 必须是 feature label 字符串或非负整数 feature ID 的数组，例如 [\"door_upper_neg\", 6823]"。
3. 错误信息里的依赖列表已经是机器可读 JSON（这点很好），建议顺手在 message 里附上"可直接将以上 feature_id 追加到 targets 重试"。

### P5 原生失败的错误信息不指名失败字段（与 P1 相关但独立成立）

`draft` 有 `surfaces[]`（拔模面集合）与 `neutral_plane`（中性面）两个引用参数。"Plane reference must identify exactly one surface" 出现时无法区分是哪个参数解析失败——本次是通过逐项替换才定位到 `neutral_plane`。同类问题在 `project_curve`（target/source/direction_ref 三参数）上也会出现。

**建议**：失败信息模板加一个 `failed_reference` 字段（参数名 + 传入值 + 解析结果/候选数），一次到位。

## 三、给作者的优先级建议

1. **P2**（多会话选择：无人值守场景的硬阻断；至少先改错误信息，说明"配置后需重启服务"）。
2. **P1**（draft neutral_plane 文档示例修正 + 双形式语义说明；一行文档改动可避免大量踩坑）。
3. **P3**（大模型超时预算动态化 + 阶段进度；unknown_outcome 的"疑似成功"捷径）。
4. **P4/P5**（删除级联的自动化开关、引用解析失败的 failed_reference 字段）。
5. 历史 P10（extrude draft_angle）与 P9（预览着色）继续保留在 backlog——本次大模型上每特征 1~2 分钟的再生时间也让"预览自动验证闭环"的价值更高。

## 四、复现清单（给作者的最小用例）

```jsonc
// P1: 在一个已有多个水平面的模型上（如 40x20x30 方块 + 顶面另一方块）:
{"op":"draft","label":"d1","angle":15,
 "surfaces":[{"kind":"surface","id":<某个竖直侧面id>}],
 "neutral_plane":{"kind":"datum_plane","axis":"z","offset":0}}
// 期望：成功或明确报"哪个引用、几个候选面"
// 实测：Plane reference must identify exactly one surface（~2 分钟后才失败，不指名字段）
// 改为 {"kind":"plane","normal":[0,0,1],"offset":0} 即成功

// P4: 删除一个 execute_plan 创建的 sketch+extrude 对:
{"op":"feature_state","action":"delete","targets":["sk_label","ex_label"]}
// 期望：成功，或失败信息给出可重试的完整 ID 列表（现行为已较好）
// 注意 targets 是裸数组，不是 [{kind:feature,label}] 对象
```
