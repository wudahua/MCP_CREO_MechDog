# 给软件工程师看的 Creo MCP 改动说明

维护者有软件工程经验，但不熟悉机械设计和 Creo。解释方案、修复或验收时，先让维护者看懂要解决的问题、关键因果和判断依据，再提供 SDK 与源码追溯。本文是沟通方式，不增加运行权限、审批步骤、工具或新的几何能力。

“让维护者能核对”是让结论可理解、可追查，不是把技术验证交给维护者。默认由开发 AI 取得依据、执行已获准的检查并报告结论；不让用户手工建参照、确认树节点或根据画面签认几何正确。用户决定目标与必要授权，无法自动确定的真实设计输入再具体询问。

## 1. 先回答维护者能核对的五件事

行为改动或疑难修复，先给简短中文说明；内容按下表组织，不要求固定五个标题。小修复可合成几句，纯文档整理只说明实际资料变化及检查；概念问答直接回答，不机械套长模板。沿用工作卡、PR 和聊天记录，不为每个改动另建一份报告。

| 要回答的问题 | 应写出的内容 |
| --- | --- |
| 用户会看到什么变化 | 一个具体输入场景、原先结果与修改后目标；说清保留什么行为、改变什么行为 |
| 原来为什么错 | 已复现现象、已证实原因和仍是推测的部分；必要术语首次出现时用一句话解释 |
| 为什么这样改有用 | 把错误判断或失败步骤与修改对应起来；写出关键条件的前后差别，不只列函数名 |
| 怎样判断做对了 | 事先确定的预期及来源、实际结果与原始证据、失败时如何判定；缺少实测就给待执行方法，不填写假结果 |
| 还不能证明什么 | 本次环境/版本、未测输入与阶段、几何之外的工程条件及剩余依赖；区分部分交付、诊断改善和功能修复 |

方案阶段先给目标、原因假设和验收办法；进度说明本次确认了什么、还缺什么证据、下一步会核对什么。交付阶段再补实际结果及范围。使用可核对的因果摘要，不复述冗长检索过程，也不把猜测写成根因。

先解释用户行为、输入输出和状态变化；API、元素树、长日志、测试数量、job_id、提交与指纹放在后面的证据链接或补充信息中。它们便于追溯，但不会自动证明改动符合需求。用户要求深入时继续提供具体实现。

## 2. 把“对不对”分成三种判断

| 层次 | 维护者要看的问题 | 对应证据及边界 |
| --- | --- | --- |
| 软件契约 | 校验、错误处理、revision、并发、状态变化及回滚是否按约定工作 | 输入输出、代码条件、日志和适用测试；软件契约通过不等于形状正确 |
| CAD 几何 | 原生特征、尺寸、形状、位置及保存后结果是否符合输入目标 | 目标环境的原生测量、实际模型、保存重载和适用反例；几何通过不等于工程功能通过 |
| 机械工程 | 配合、承载、密封、材料或工艺是否满足使用要求 | 对应工程依据、分析或试验；缺条件时标未验证，需要专业判断的选择明确提出 |

软件维护者可以核对契约与证据链，几何判断优先转成可测目标；不能暗示仅阅读 SDK、看到预览或委托另一个 AI 就能代替机械工程判断。也不要求每个纯软件改动都经过机械专家审批，按实际影响划定边界。

### 验收预期要有独立来源

实现和测试可能共享同一个错误假设。为关键行为给出 **预期依据 → 预期值/条件 → 实际值/条件 → 证据位置**，例如：

- 用户明确给出的尺寸或行为约定；
- 简单、可复算的解析例子，例如长方体体积；
- 有明确来源、验收依据和适用条件的参照模型，由开发 AI 先核对；人工确认是可用来源之一，不要求维护者亲自评价其几何；
- 官方明确的接口契约，用于核对该层软件/API 行为。

不要只把产品函数的输出再调用一遍当作独立期望，不把输入参数回显当成 Creo 测量，不在看到失败结果后放宽容差或改目标凑通过。独立算例只证明其适用范围，前后体积相同也不能单独证明所有形状、拓扑及位置都正确；应同时检查这次需求指定的关键变化。

白话解释也不能把指标说成更强的结论。例如“体积相同”只支持净体积未变，不能排除一处加料、另一处减料，也不能单独证明原有几何完全没动。若要证明这些性质，还需相应几何对照；没有测到某种变化，不直接写成所有相关变化都不存在。

另一个 AI 的审阅可帮助发现问题，但仍需上述依据和可复查结果。单元测试、SDK 查证、本次实机、历史证据分别标注；版本和失败阶段也分别核对，不能由某版本某一步成功推导其它版本整条链都成功。

## 3. 用熟悉的概念解释，保留可追查细节

可以用软件经验帮助理解，例如“调用返回成功后还需核对业务结果”“模型原有状态与本次事务效果要分开”。类比只解释相似的判断关系，不把几何/工程问题等同于 SQL 或事务问题。

术语只解释当前任务需要的部分，例如“再生”可先说成“让 Creo 按特征与参数重新计算模型”。给出具体效果与限制，不要求维护者先通读机械术语表。

涉及位置或形状时，可以提供标注测量位置的实际模型前后对照；示意图明确标为示意，真实预览说明产物与坐标来源。没有本次实际几何就说明暂缺，不用生成图片或旧截图充当验收。本次文档说明本身不授权新建模、截图或会话操作；执行边界仍按 [AGENTS](../../AGENTS.md)。

## 4. 示例：把专业描述改成可审阅说明

以下是历史记录的说明示范，不是本次重新测试，也不是对当前所有输入/版本的支持声明。实际使用时核对相关工作卡当前摘要，历史原件保持原样。

### BUG-119：保留实体并增加曲面

技术线索是“模型级 `has_solid` 被当成本次操作效果”。面向维护者应先说：

**目标与错误**：原模型已经有一个有体积的实体，现在只想增加一张曲面。程序原来只要看见模型有实体就报错，把原有材料误认为本次新增材料。

**修改理由**：改成比较操作前后本次是否新增实体材料，保留对真正违规结果的拒绝。软件层可以理解为把“原来就有”与“这次新增”分开判断。

**开发 AI 怎样验证并汇报**：准备已知的 100×60×10 mm 长方体，独立算出预期体积 60000 mm³；在本次实机授权范围内执行增加曲面、原生测量和保存后检查。原材料不应增加，目标曲面还须存在且形状/面积符合算例；不能只凭体积没变就断定曲面正确。开发 AI 给维护者前后结果、判断及证据，不要求维护者亲自建模和确认；无授权时只完成方案与离线依据，明确待测。

[BUG-119 的验证记录](../work-items/BUG-119.md) 记载，2026-11-12 Creo 12.4.0.0 的该算例材料体为 1→1，体积为 60000→60000 mm³，新增曲面面积约 5026.55 mm²（完整精度见原记录），保存重载验证通过。上述是工作卡历史实测，本次未复测；它不证明其它版本、任意复杂曲面或机械性能已经通过。

源码追查需要时再看字段、阈值和原生实现；维护者先确认目标、判断范围和证据是否相符。

### BUG-123：模板路线成功的适用范围

“用 XML 模板建树，11 项通过”需要解释为：换了一种准备特征创建输入的方法；应再说明它改变的是哪个步骤，以及原故障是否发生在这个步骤。

[BUG-123](../work-items/BUG-123.md) 的 2026-11-13 阶段记录中，Creo 12.4 的手写与模板两条路线在该算例的面积均为 1600 mm²。但 [BUG-120](../work-items/BUG-120.md) 的原始 Creo 10 问题包含创建后的结构回读失败，模板路线仍保留这一步。所以该阶段证据支持“12.4 这个算例两条输入路线一致”，尚不支持“Creo 10 的原故障已修好”。

对维护者还应报告该阶段保留的兼容复测、模板交付/打包等范围；读头文件确认有函数或在另一版本跑通，都不能跳过这些缺口。后续实现若有新证据，以新记录更新当前结论，不改写这段历史示例。

## 5. 与现有开发和验收规则一起使用

技术依据与接入方法见 [开发指南](CREO_TOOLKIT_GUIDE.md)，实际模型证据和原生交付见 [验收专题](CREO_MODELING_ACCEPTANCE.md)。说明方式不减少检查和追溯，也不增加“每一步都等用户确认”的流程；已授权工作继续推进，只对影响目标且无法查明的设计选择或原有规则要求的权限另行处理。

仅 WorkBuddy 黑盒验收仍走 skill 首段分流：使用公开 MCP 行为和可见证据，不读源码/SDK/配置/Git，不把本专题的开发者查证流程交给 WorkBuddy。没有实机授权时，说明待测方法和未验证范围，不为补齐报告自行连接 Creo。
